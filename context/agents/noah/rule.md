# 任务规划规则

## 强制要求

1. 必须调用 `task_writers` 创建任务树；只输出文字视为失败。
2. 完成前必须调用 `task_lists()` 自检。
3. 每个叶子任务必须包含技术栈标签、优先级、文件路径、具体动作、验收条件。
4. 一个叶子任务只能属于一种技术栈：`[Backend]`、`[Backend:Go]`、`[Backend:Python]`、`[Frontend]`、`[Test:*]`、`[Doc]`。
5. 每个阶段父任务必须有 `phase` 和描述交付物的 `phase_label`。
6. 叶子任务应设置最相关的 `task_doc`；没有可用详情文档时在描述中说明原因。
7. 依赖关系必须无环；有前置条件时写入 `depends_on` 或任务描述。
8. 每个 phase 的叶子任务总量必须控制在单次会话可完成的范围（通常 2-5 个）；若超出则拆分为多个 phase。

## 质量红线

- 不得遗漏设计中明确的 Must 功能。
- 不得把测试和开发合并到同一叶子任务。
- 不得创建”实现功能””完善页面”等无法直接执行的模糊任务。

> 正例：`[P0][Backend:Go] 新增 POST /api/users 接口含参数校验 — src/controller/user.go`
> 反例：`[P0][Backend:Go] 实现用户模块`（无具体动作、无文件路径、粒度过大）

- 不得创建单个叶子任务过大（涉及 3 个以上文件的大规模变更）或单个 phase 任务过多（超过 5 个叶子）的规划。
- 测试任务必须按项目实际需要覆盖单元、接口、E2E 或集成测试。

## 异常处理

- 需求或设计不足：创建可执行部分，并在相关任务中标注 `[待确认]` 和具体问题。
- 当前文档与项目结构冲突：以项目实际结构为准，并在任务描述中说明调整。
- 任务过大：继续拆分；任务过小且同文件同目标：合并。
