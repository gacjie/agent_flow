# UI/UX 设计规则

## 强制要求

1. 设计前必须读取需求文档和技术规范，理解项目技术栈和前端方案。
2. 已有项目必须先读取现有 CSS/模板/布局文件，继承已有视觉体系。
3. 全局规则中的 CSS 变量必须使用具体数值，禁止用"适当"、"合适"、"较大"等模糊词。
4. 组件代码必须使用全局规则中定义的 CSS 变量，禁止硬编码颜色/间距/字号。
5. 配色方案必须同时提供亮色和暗色主题变量（除非需求明确只需单主题）。
6. 间距和字号必须基于统一基准单位，使用倍数关系（如 4px × 1/2/3/4/6/8）。
7. 组件 HTML 结构必须使用语义化标签和 BEM 或项目已有命名规范。
8. 响应式设计必须至少覆盖移动端（≤768px）和桌面端（>1024px）两个断点。
9. 只有指令明确给出路径时才写入工作文档。
10. 新建项目的配色和字体决策必须基于调研参考得出，禁止在未查看任何参考的情况下直接输出方案。产出中须标注设计决策依据（如"参考 XX 站点的配色比例""用户需求暗示 XX 方向"）。
11. **参考的作用是补全用户需求的空白，不是覆盖用户已明确的要求。** 逐个设计维度判断：用户需求是否对该维度有明确要求（布局、配色、风格、交互等）？有 → 遵循用户需求；无 → 用参考项目补全。禁止在用户已明确要求的维度上使用参考站点的方案。
12. **优先级规则**：用户明确的前端需求（任何维度）> 参考站点对应维度的方案 > 项目类型默认惯例。任何设计决策点发生冲突时按此顺序裁决。

## 质量红线

- `specs/ui-patterns.md` 只放规则约定（变量定义、配色逻辑、间距节奏、字体层级、主题方式），不放具体组件代码。
- `tasks/ui-patterns-{scope}.md` 放具体组件 HTML/CSS 代码，每个模块 2-5 个关键组件。
- 组件代码必须是可直接使用的完整代码片段，不是伪代码或示意。
- 配色对比度必须满足 WCAG AA 标准（文字与背景 >= 4.5:1）。

## 禁止事项

- 禁止未读项目现有前端代码就设计全新体系（已有项目场景）。
- 禁止使用需要额外构建工具的语法（如 SCSS/Less/Tailwind），除非项目已使用。
- 禁止产出纯文字描述性设计文档而无具体 CSS 变量和代码片段。
- 禁止输出与需求文档技术约束冲突的方案（如需求要求原生 CSS 却输出 Tailwind）。
- 禁止完成指令要求的任务后继续执行职责范围外的工作；任务完成即停止回复结果。

## 异常处理

- 用户未描述风格：先通过 web_searches 搜索同类产品视觉参考，基于调研结果结合项目类型决策（管理后台→简洁专业、营销页→视觉冲击、工具型→高效紧凑），标注参考来源和假设。此时参考可提供全面的视觉方案作为补全。
- 用户只描述了部分需求（如只说了功能未说布局）：参考同类型项目补全未提及的部分，但用户已明确的部分不得被参考覆盖。产出中须标注哪些决策来自用户需求、哪些来自参考补全。
- 已有项目风格不一致：以主 CSS 文件和布局模板为准，记录差异。
- 无参考站点可用：使用 web_searches 搜索同类产品截图或设计系统作为参考。
