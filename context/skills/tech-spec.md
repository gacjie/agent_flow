# 技术规范文档编写指南

本技能定义了技术规范文档（tech-spec）的标准结构。架构师在扫描项目后，按此结构输出规范文档，作为后续设计和开发的约束基准。

## 文档结构

技术规范文档必须包含以下 5 个章节，每个章节都有明确的格式要求。

---

### 1. 命名约定

为项目中所有命名场景制定统一规则，消除前后端命名不一致的根源。

必须覆盖的命名场景：

| 场景 | 需要定义的内容 | 示例 |
|------|--------------|------|
| 后端变量/字段 | casing 规则 | snake_case |
| 后端函数/方法 | casing 规则 | snake_case（Python）/ CamelCase（Go） |
| 后端类/结构体 | casing 规则 | PascalCase |
| 数据库表名 | casing + 单复数 | snake_case 复数（users） |
| 数据库字段名 | casing 规则 | snake_case |
| API URL 路径 | casing + 层级规则 | /api/v1/user-groups（kebab-case） |
| URL 查询参数 | casing 规则 | snake_case（page_size） |
| JSON 请求/响应字段 | casing 规则 | snake_case 或 camelCase（必须统一） |
| 前端 JS 变量 | casing 规则 | camelCase |
| 前端 CSS 类名 | 命名方法论 | BEM / kebab-case |
| 文件名 | casing + 分隔符 | snake_case（Python）/ kebab-case（前端） |

**关键约定**：当后端和前端的 casing 规则不同时（如后端 snake_case、前端 camelCase），必须明确转换规则和转换位置（前端接收时转换 / 后端序列化时转换）。

---

### 2. API 契约 Schema

为每个 API 端点定义完整的请求/响应结构。这是消除前后端不一致的核心章节。

每个端点必须包含以下信息：

```
### {HTTP方法} {完整路径}

**描述**：{一句话说明}

**路径参数**：
| 参数 | 类型 | 说明 |
|------|------|------|
| id | int | 资源 ID |

**查询参数**：
| 参数 | 类型 | 必填 | 默认值 | 说明 |
|------|------|------|--------|------|
| page | int | 否 | 1 | 页码 |
| page_size | int | 否 | 20 | 每页数量 |

**请求体**（JSON）：
| 字段 | 类型 | 必填 | 约束 | 示例 |
|------|------|------|------|------|
| name | string | 是 | 1-50字符 | "张三" |
| email | string | 是 | 邮箱格式 | "user@example.com" |

**成功响应**（200）：
| 字段 | 类型 | 说明 | 示例 |
|------|------|------|------|
| code | int | 状态码 | 0 |
| message | string | 提示信息 | "success" |
| data | object | 业务数据 | {...} |

**错误响应**：
| HTTP 状态码 | 业务错误码 | 说明 |
|------------|-----------|------|
| 400 | INVALID_PARAM | 参数校验失败 |
| 404 | NOT_FOUND | 资源不存在 |
```

**编写原则**：
- 字段名必须与命名约定章节一致
- 每个字段都要有类型和示例值
- 嵌套对象需要展开定义
- 数组类型标注元素类型（如 `[]object`）

---

### 3. 错误码体系

定义全局统一的错误处理规范。

HTTP 状态码详细语义见 skills/api-design.md

**统一错误响应格式**：
```json
{
  "code": "错误码（int 或 string，需统一）",
  "message": "用户可读的错误描述"
}
```

**业务错误码命名规则**（如果使用字符串错误码）：
- 格式：`{MODULE}_{ERROR_TYPE}`
- 示例：`USER_NOT_FOUND`、`AUTH_TOKEN_EXPIRED`

---

### 4. 状态值定义

所有枚举和状态值的统一定义，确保前后端使用相同的值和含义。

格式：

```
#### {实体名} 状态

| 值 | 常量名 | 含义 | 前端显示文本 |
|----|--------|------|-------------|
| 0 | PENDING | 待处理 | 待处理 |
| 1 | ACTIVE | 进行中 | 进行中 |
| 2 | COMPLETED | 已完成 | 已完成 |
```

**编写原则**：
- 每个枚举值都要有常量名（后端使用）和显示文本（前端使用）
- 值的类型统一（全用 int 或全用 string）
- 新增状态值必须在此文档中登记

---

### 5. 数据格式约定

跨模块通用的数据格式规范。

需要定义的格式：

| 格式项 | 需要定义的内容 | 示例 |
|--------|--------------|------|
| 日期时间 | 格式字符串 | "2006-01-02 15:04:05" |
| 仅日期 | 格式字符串 | "2006-01-02" |
| 分页请求参数 | 参数名 | page + page_size 或 offset + limit |
| 分页响应结构 | 字段名和类型 | total/page/page_size/items |
| 排序参数 | 参数名和格式 | sort=field:asc,field2:desc |
| 布尔值 | 表示方式 | true/false（JSON）或 1/0（查询参数） |
| 空值 | 处理方式 | null / 不返回该字段 / 返回默认值 |
| ID 格式 | 类型 | 自增 int / UUID string |

---

## 编写流程

1. **扫描项目**：读取现有代码，提取已有的命名规范和数据格式
2. **现有项目**：以已有规范为准，整理成文档格式，不发明新规范
3. **新项目**：根据技术栈的社区最佳实践制定规范
4. **输出文档**：按上述 5 个章节结构输出，使用 write_contexts(name="tech-spec") 写入工作区
