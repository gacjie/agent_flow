# 任务规划工作流

## 1. 读取输入

- 从自动加载的 `specs/` 中提取需求、技术规范、设计摘要。
- 调用 `list_work_docs(scope="tasks")`，再用 `analysis_work_docs` 快速识别详细设计和接口契约。
- 建立“模块 -> 详情文档 -> 涉及技术栈”的映射。

## 2. 勘察项目

用 `list_files` 确认相关目录和文件是否存在，判断任务是新增、修改还是扩展。文件路径必须按项目实际结构填写。

## 3. 拆分任务

按模块列出文件级变更，拆成叶子任务：
- 标题格式：`[P级][技术栈] 动作对象 — 文件路径`

> 标题示例：
> - `[P0][Backend:Go] 新增用户模型和数据库迁移 — src/model/user.go`
> - `[P1][Frontend] 实现用户列表页和分页交互 — templates/admin/user_list.html`
> - `[P0][Backend:Python] 添加 JWT 认证中间件 — app/middleware/auth.py`
- 描述包含：要做什么、涉及文件、验收条件、依赖或待确认点。
- 任务粒度：一个专家、一个技术栈、一次会话可完成。

## 4. 组织阶段

### 阶段划分原则

- 每个 phase 只含一种技术栈，由一个专家在一次会话中完成。
- 阶段应内聚、可交付、可压缩；每阶段通常 2-5 个叶子任务。
- 设计中包含多个功能模块时，每个模块必须独立成 phase，禁止将多模块合并到同一 phase。

### 阶段排序规则

按依赖关系从底层到上层排列：
1. 基础设施层（P0）：项目骨架、数据库连接、配置加载、公共中间件等被所有模块依赖的代码。
2. 公共/共享层（P0）：基类模型、通用服务、认证鉴权、基础模板和布局等多模块复用的代码。服务端模板项目中此层必须包含基础模板（含全局 header/sidebar/footer/nav）的创建任务；后续模块层的页面任务验收条件须包含"继承基础模板、全局布局与公共层一致"。
3. 模块层（P1）：每个业务模块独立成 phase，按模块间依赖顺序排列（被依赖的模块在前）。
4. 测试层（P2）：开发全部完成后统一测试。
5. 文档层（P2）：功能稳定后撰写文档。

### 划分方式选择

根据模块间依赖关系和项目类型选择最合适的方式：

- 后端优先模式（模块间接口依赖较多时）：后端基础设施 -> 后端公共 -> 后端各模块（每模块一个 phase）-> 前端公共 -> 前端各模块（每模块一个 phase）-> 测试 -> 文档。
- 模块交替模式（模块较独立、前后端对应关系明确时）：后端基础设施 -> 后端公共 -> 前端公共 -> 后端模块A -> 前端模块A -> 后端模块B -> 前端模块B -> ... -> 测试 -> 文档。
- 单模块增量：后端变更 -> 前端变更 -> 测试。

选择依据：模块间接口依赖多时用后端优先（避免前端因后续接口变动返工）；模块独立性强时用交替模式（每个模块尽快完整可验证）。

### 模块拆分判定

当设计文档中存在多个 `tasks/design-{scope}.md` 时，每个 scope 对应的后端实现和前端实现各自独立成 phase。

> 阶段划分示例（多模块全栈项目）：
> - Phase-1 [Backend:Python] 基础设施：项目骨架、数据库初始化、配置加载、路由注册（3 个叶子）
> - Phase-2 [Backend:Python] 公共层：基类模型、认证中间件、权限装饰器、会话管理（4 个叶子）
> - Phase-3 [Backend:Python] 用户管理模块：用户模型、用户服务、用户控制器（3 个叶子）
> - Phase-4 [Backend:Python] 权限管理模块：角色模型、权限服务、角色控制器（3 个叶子）
> - Phase-5 [Frontend] 公共前端：基础布局模板、公共 CSS/JS、主题切换（3 个叶子）
> - Phase-6 [Frontend] 用户管理页面：用户列表页、用户表单页、用户详情页（3 个叶子）
> - Phase-7 [Frontend] 权限管理页面：角色列表页、权限分配页（2 个叶子）
> - Phase-8 [Test:API] 接口测试（2-3 个叶子）
> - Phase-9 [Doc] 项目文档（2 个叶子）

> 阶段划分示例（单模块增量）：
> - Phase-1 [Backend:Go] 操作日志模块：日志模型、日志服务、日志接口（3 个叶子）
> - Phase-2 [Frontend] 操作日志页面：日志列表页、日志筛选组件（2 个叶子）
> - Phase-3 [Test:API] 日志接口测试（2 个叶子）

### 需求符合性检查

写入任务前回溯验证：
- 需求文档中的 Must 功能是否全部有对应叶子任务覆盖。
- 设计文档中的架构约束（应用边界、模块划分）是否在任务结构中正确体现。
- 任务的文件路径是否与设计文档中的文件结构一致。

## 5. 写入与自检

1. 先用 `task_writers` 创建阶段父任务。
2. 记录父任务 ID 后，再用 `task_writers` 创建叶子任务。
3. 为叶子任务设置 `parent_id`、`priority`、必要的 `task_doc` 和依赖信息。
4. 调用 `task_lists()` 自检父子结构、标签、文档关联、任务粒度和覆盖范围。
5. 回复中只总结阶段数量、任务数量、自检结果和待确认点。
