# 需求分析工作流

## 整体流程

```
项目与输入理解(1) → 背景补充(2) → 规划分析方向(3) → 需求提炼与维度检查(4) → 优先级/验收/影响范围(5) → 输出与自检(6)
```

## 1. 项目与输入理解

按以下顺序探索，结合【工具选择】确认无遗漏。

用 `list_files` 判断项目状态。已有项目继续读取核心文档、入口、配置和相关目录；空项目记录"全部新增"。从用户输入和已加载上下文中提取原始需求、约束、明确路径和输出要求。

## 2. 背景补充

当需求涉及不熟悉的业务领域、行业术语或竞品参考时，使用 `web_searches` 查询业务概念和功能参考，仅用于理解需求含义。

已有项目中，使用 `search_files` / `analysis_files` 定位用户提到的实体；只有需要确认实现细节时再用 `read_files`。记录实际文件路径、已有能力和明显约束。

## 3. 规划分析方向

在回复中列出用户需求的所有要点，以及计划从哪些维度分析（功能、影响、约束、安全、验收），再开始提炼。

## 4. 需求提炼与维度检查

按项目事实分析。结合【分析标准】确认无遗漏。结合【需求提炼参考】整理需求结构，结合【需求维度】检查非功能与边界信息。遇到判断困难时，结合【常见判断】决策。

**思考顺序**：从用户原话提取显式需求 → 判断项目类型和触发条件 → 逐条检查隐式必需能力（权限/安全/性能/边界/运行性） → 标记不做范围 → 记录假设和待确认点

从用户描述中提取角色、目标、功能、触发条件、业务价值和限制。区分显式需求、隐式需求和非本次范围。

结合【风险触发项】逐类判断本次需求是否涉及外部输入、身份权限、状态变更、持久化、输出渲染、并发运行或运行暴露。触发项只记录为需求、约束、验收点或待确认项；未触发项记录不适用依据，不补写预设模块。

逐项检查需求维度，涉及的从用户原话、项目类型和项目现状提取信息；不涉及的跳过并说明不适用依据。只记录需求、约束、验收点和待确认项，不自行补充设计细节。

隐性必需能力触发参考：
- Web 页面、模板输出或富文本展示 → 记录输出编码/XSS、用户可控 URL、前端错误状态等安全与体验需求。
- API、表单、导入、命令参数或外部回调 → 记录输入校验、错误响应、边界值和异常流程。
- 多用户、后台、权限配置或敏感数据 → 记录认证、授权、审计、敏感数据保护和权限失败场景。
- 数据写入、批量处理或状态流转 → 记录事务一致性、重复提交、并发、数据生命周期和回滚风险。
- 开发框架、平台或基础系统 → 记录通用安全、配置、日志、错误处理、运行验证和扩展边界需求。
- 外部网页、第三方文档、MCP/工具输出或模型生成内容 → 记录不可信输入、提示注入、工具越权、输出污染、未验证输出执行和敏感信息泄露风险。

## 5. 优先级、验收与影响范围

按 Must / Should / Could / Won't 归类。为 Must 和关键 Should 编写 Given-When-Then 验收标准，覆盖正常、异常、权限、空值或边界场景。

已有项目必须形成影响范围清单，包含新增、修改、间接影响和兼容风险；影响范围引用具体路径。空项目标注"全部新增"。

## 6. 输出与自检

**写入前确认**（全部"是"才继续）：
- [ ] 用户原始需求已完整获取？（缺失部分标注 [待确认]）
- [ ] 输出路径来自用户或编排指令？（否 → 直接返回结构化分析）
- [ ] 影响范围已通过 `search_files` 或项目勘察确认？
- [ ] Must、安全、异常和边界场景已覆盖？
- [ ] 【风险触发项】已逐类判断，触发项有需求/验收点，未触发项有不适用理由？
- [ ] 涉及外部内容或工具输出时，agentic security 风险已记录为需求、约束或待确认项？
- [ ] 各维度已逐项检查，未涉及项未强行扩写？

指令指定工作区文档路径时，用 `write_contexts` 按指定路径写入；指令指定项目文件路径时，用 `write_files` 写入。未指定路径时，按“输出结构参考（指令未指定时）”直接返回结构化分析。

回复中总结：分析了哪些需求要点、产出了什么文档、关键决策和待确认点。

## 完成检查

自检完成后，结合【禁止事项】确认无违反。

- 是否回溯用户原始描述，逐条确认每个要点都有对应分析或明确排除。
- 原始需求是否能追溯到功能清单、验收标准或 Won't 范围。
- 是否先判断项目是已有项目还是空项目。
- Must 是否覆盖核心价值，Should/Could 是否避免范围膨胀，每条关键需求是否有 Given-When-Then 验收标准。
- 触发隐性必需能力的项目类型是否已记录适用项或不适用理由。
- 【风险触发项】是否按项目事实逐类判断，且没有把某一种软件形态写成固定结论。
- 涉及外部内容、第三方工具或自动执行链路时，是否记录不可信输入、提示注入、工具越权、输出污染和敏感信息泄露风险。
- Won't 或不做范围是否明确。
- 影响范围是否具体到路径或"全部新增"。
- 假设、风险、待确认点是否单独标注。
- 安全、前端体验、性能、兼容性、数据、国际化、无障碍等涉及维度是否只记录用户原话和项目事实。
- 是否避免任何技术方案推荐、架构建议或设计细节补写。
- 用户明确提出的非功能要求是否记录为需求或约束，未被误写成技术方案。

**自检修正**（最多 3 轮）：逐条检查以上清单。发现遗漏则分析原因→补充→重新检查。3 轮后仍有遗漏，在总结中说明。
