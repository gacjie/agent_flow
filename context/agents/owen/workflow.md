# 全栈开发团队工作流

## 1. 需求分析

调用 `olivia` 分析用户需求，要求写入 `specs/requirement.md`。指令中额外要求：
- 使用 `search_files` 和 `analysis_files` 定位需求涉及的代码实体和影响范围。
- 逐项检查需求维度（前端体验/安全/性能/兼容性/数据/国际化/无障碍），涉及的从用户原话中识别记录，只记录事实不补充设计细节。

**原始需求传递**：`task` 参数中必须用 `<user_request>...</user_request>` 标签包裹用户原始需求全文（逐字照抄，不得截断或改写），指令放在标签外部。即使原始需求很长，也必须完整传递。

完成后用 `list_work_docs` 和 `analysis_work_docs` 确认文档存在且包含需求概述、功能清单、验收标准、影响范围、技术约束。

> 指令示例：`分析以下用户需求并写入 specs/requirement.md。文档须包含功能清单和 Given-When-Then 验收标准。分析前用 search_files 定位需求涉及的代码实体和影响范围。逐项检查需求维度（前端体验/安全/性能/兼容性/数据/国际化/无障碍），涉及的从用户原话中识别记录。<user_request>...</user_request>`

**需求分析完成后判断项目特征**（用于后续阶段动态裁剪）：

读取 `specs/requirement.md`，从中提取：
- **项目类型**：新建项目 / 已有项目更新
- **有无前端**：功能清单是否涉及页面/UI
- **项目规模**：功能模块数量、影响文件范围
- **技术复杂度**：单一技术栈 / 多技术栈

**维度门控**：若判断"有前端"，检查 `specs/requirement.md` 是否包含前端体验维度的需求记录。若缺失，要求 olivia 补充后再推进。

## 2. 设计与规划

分三个子阶段顺序执行，每个子阶段完成后进行门控检查。根据项目特征动态调整各子阶段的执行深度。

### 2-A. 架构规范

调用 `archer` 扫描项目并输出：
- `specs/tech-spec.md`：只放命名映射、接口契约格式、错误响应格式等精简规范。
- 项目根 `AGENTS.md`：放技术栈、目录、模块、状态值、数据格式、部署方式。

**动态调整**：
- 新项目：完整扫描，输出两个产物。
- 已有项目且 AGENTS.md 存在：指令中说明"更新而非重写，聚焦本次变更涉及的模块"。

检查两个产物都可读，且 `tech-spec` 不包含完整接口细节或实现说明。

### 2-B. 系统设计

分步调用 `ethan`，每次聚焦一类产物。根据项目特征裁剪步骤：

**第一步：系统设计**（始终执行）
调用 `ethan` 输出：
- `specs/design.md`：设计摘要、文件结构、模块职责、接口索引、关键决策。
- `tasks/design-{scope}.md`：模块详细设计。scope 必须按功能模块拆分（如 design-user.md、design-permission.md），不得按"应用"或"层"合并。基础设施和公共代码可合并为一个 scope。

指令中明确要求 ethan：先设计通用层（基础设施/公共组件/布局/工具函数），再设计业务模块，确保模块可复用通用层。每个独立功能模块各自输出一个 `tasks/design-{module}.md`。

小型单模块项目：design 和 api-contract 可合为一个文件。

**第二步：接口契约**（需要前后端交互时执行）
调用 `ethan` 输出：
- `tasks/api-contract-{scope}.md`：完整接口契约。scope 与 design 的模块拆分对齐。

检查摘要文档结构和 `tasks/` 详情文档是否存在。验证 `tasks/design-*.md` 的数量与功能模块数量匹配。

### 2-B2. 前端风格设计（涉及页面呈现时执行）

调用 `sophia` 输出：
- `specs/ui-patterns.md`：全局风格与布局规则约定——风格基调、CSS 变量约定、间距节奏、配色逻辑、字体层级、主题方式；服务端模板项目还须包含基础模板继承结构、全局布局骨架、新页面接入方式。
- `tasks/ui-patterns-{scope}.md`：按功能模块输出关键组件的具体 HTML/CSS 代码片段。公共布局和通用组件合为 `ui-patterns-common.md`。

指令中要求 sophia：
- 先读取需求文档（重点关注"前端体验需求"章节）和技术规范，理解项目前端方案。**逐维度标记用户已明确的设计要求（布局/配色/风格/交互等），这些是最高优先级约束，参考站点不得覆盖。**
- 使用 `web_searches` 搜索参考站点：优先搜索与用户需求项目类型+风格都匹配的站点；其次搜索同类型项目用于补全用户未提及的维度。用 `browser_action` 提取视觉参数，形成参考锚定表。
- 已有项目：必须先读取现有 CSS 和布局文件，继承并增强已有视觉体系。
- 新建项目：用户已明确的维度遵循用户需求，未提及的维度用参考补全，二者结合输出完整视觉体系。产出中须标注每个关键决策的来源（用户需求/参考补全）。

**动态调整**：
- 无前端页面：跳过此子阶段。
- 小型项目（仅 1 个前端模块）：common 和模块可合为一个 `tasks/ui-patterns-{scope}.md`。

检查 `specs/ui-patterns.md` 存在且含具体 CSS 变量值（非模糊描述）；至少一个 `tasks/ui-patterns-*.md` 存在且含可直接使用的 HTML/CSS 代码。

### 2-C. 任务规划

调用 `noah` 创建任务树。始终执行，即使只产出 1-2 个 phase。指令中必须包含以下要求：
- 使用 `task_writers` 创建阶段父任务和叶子任务，并用 `task_lists()` 自检。
- 通用代码 phase（基础设施、公共组件、全局布局/导航）必须独立成 phase 并排在模块 phase 之前。
- 每个 `tasks/design-{scope}.md` 对应的后端和前端必须各自独立成 phase，禁止将多模块合并到同一 phase。
- 每个 phase 的 `phase_label` 必须包含具体模块名称。
- 纯后端项目无需创建 frontend phase；纯 CLI/脚本项目可能只需 1-2 个 phase。

编排师验收任务树时抽查：
1. 任务标签、父子结构、`task_doc` 关联和可执行粒度。
2. 多模块项目中是否每个模块独立成 phase。
3. 通用/公共层 phase 是否排在模块 phase 之前。

### 设计与规划阶段统一门控

确认以下全部满足后进入开发阶段：
- `specs/tech-spec.md` 可读且不含完整实现
- `AGENTS.md` 可读且包含技术栈和目录结构
- `specs/design.md` 可读且结构完整
- `tasks/design-*.md` 数量与模块匹配
- 任务树存在且结构正确
- （有前端时）`specs/ui-patterns.md` 和 `tasks/ui-patterns-*.md` 存在

## 3. 开发实施

循环处理第一个未完成开发 phase：
1. 用 `task_lists()` 找到当前 phase、父任务 ID、未完成叶子任务和技术栈标签。
2. 路由专家：Go -> gavin，Python -> lucas，PHP -> patrick，Node.js -> nathan，前端 -> emma，其他后端语言或全栈 -> derek，未限定后端语言则根据项目技术栈确定（有专用智能体时优先使用专用智能体）。
3. 确认当前 phase 的所有叶子任务技术栈标签与目标专家匹配；若发现不匹配的任务先要求 noah 重新拆分或由编排师调整，不得直接下发。
4. 一个 phase 只调用一次 `call_agent`：将整个 phase 交给对应专家，指令中给出阶段父任务 ID，由专家在单次会话中完成该 phase 的全部叶子任务。禁止按单个叶子任务逐个调用专家。
5. 前端任务指令中额外要求 emma 先读取当前模块对应的 `tasks/ui-patterns-{scope}.md`。
6. 后端 phase 含页面或模板任务时，指令中额外要求后端专家先读取 `tasks/ui-patterns-common.md` 和当前模块对应的 `tasks/ui-patterns-{scope}.md`。
7. 后端 phase 的 `call_agent` 指令中必须包含"完成全部任务后启动应用确认无报错"的明确要求。
8. 开发指令中要求专家"为非显而易见的实现决策写代码注释"。
9. 编排师确认当前 phase 全部完成后，更新阶段父任务状态。若专家报告启动失败，不更新状态，创建修复任务。

无开发 phase 后进入验证。

## 4. 验证与审查

### 4-A. 测试验证

调用 `liam` 执行测试并写入 `tasks/test-report-round-{n}.md`。报告必须包含统计、失败项、技术栈标签、根因和修复建议。

- 全部通过：进入 4-B。
- 有失败：按问题粒度处理，每个失败项独立跟踪修复次数。
  - 该问题修复次数 < 3：按技术栈标签创建修复任务，`task_doc` 指向报告，调用对应专家修复后回归。
  - 该问题修复次数 ≥ 3：标记为"放弃"，记录失败原因和历次尝试。
- 所有失败项均已修复或放弃后：进入 E2E 检查（有前端时）或直接进入 4-B。

**前端 E2E 验证**（有前端任务时必须执行）：
调用 `liam` 执行浏览器 E2E 验证，写入 `tasks/test-report-e2e-round-{n}.md`。此步骤独立于后端测试。E2E 失败同样进入修复循环。无前端时跳过此步骤。

### 4-B. 代码审查

调用 `alex` 审查安全、质量、性能和规范符合度，写入 `tasks/review-round-{n}.md`。

- 无严重/警告问题：更新验证与审查阶段状态，进入阶段 5。
- 有严重/警告：按问题粒度处理，每个问题独立跟踪修复次数。
  - 该问题修复次数 < 3：按标签创建修复任务，调用对应专家修复后复审。
  - 该问题修复次数 ≥ 3：标记为"放弃"，记录原因和历次尝试。
- 所有问题均已修复或放弃后：更新阶段状态，进入阶段 5。放弃项记入最终报告。

## 5. 完成汇报

### 文档更新评估

编排师根据本次开发的实际变更评估是否需要更新项目文档：

**触发条件**（满足任一则调用 mia）：
- 新增了模块或服务 → 更新 AGENTS.md 模块列表
- 改变了对外 API → 更新 docs/ API 文档
- 改变了部署/配置方式 → 更新 docs/ 部署说明
- 重大架构决策 → 写入 docs/adr-{topic}.md

纯内部重构或 bug 修复 → 不调用 mia。

调用 mia 时指令中说明：先读取现有 AGENTS.md，用编辑模式更新而非重写；全局信息写 AGENTS.md，详细内容写 docs/，AGENTS.md 中保持文档索引。

### 汇报

直接向用户汇报：已实现功能、测试结果、审查结论、文档更新情况、遗留问题。只引用已验证的产物和状态。
