# 全栈开发团队工作流

## 1. 需求分析

调用 `olivia` 分析用户需求，要求写入 `specs/requirement.md`。完成后用 `list_work_docs` 和 `analysis_work_docs` 确认文档存在且包含需求概述、功能清单、验收标准、影响范围、技术约束。

> 指令示例：`分析以下用户需求并写入 specs/requirement.md。需求：为后台增加操作日志功能，记录管理员的增删改操作。文档须包含功能清单和 Given-When-Then 验收标准。`
> 反例：`帮我分析一下需求。`（缺少具体需求内容、产出路径和验收要求）

## 2. 架构规范

调用 `archer` 扫描项目并输出：
- `specs/tech-spec.md`：只放命名映射、接口契约格式、错误响应格式等精简规范。
- 项目根 `AGENTS.md`：放技术栈、目录、模块、状态值、数据格式、部署方式。

检查两个产物都可读，且 `tech-spec` 不包含完整接口细节或实现说明。

## 3. 系统设计

分步调用 `ethan`，每次聚焦一类产物：

**第一步：系统设计**
调用 `ethan` 输出：
- `specs/design.md`：设计摘要、文件结构、模块职责、接口索引、关键决策。
- `tasks/design-{scope}.md`：模块详细设计。

**第二步：接口契约**（需要前后端交互时）
调用 `ethan` 输出：
- `tasks/api-contract-{scope}.md`：完整接口契约。

**第三步：前端风格约定**（涉及前端时）
调用 `ethan` 输出：
- `specs/ui-patterns.md`：全局前端风格纯规则约定——风格基调、CSS 变量约定、间距节奏、配色逻辑、字体层级、主题方式（不含代码片段）。
- `tasks/ui-patterns-{scope}.md`：按模块输出关键组件的具体 HTML/CSS 代码片段，体现用户要求的视觉风格。scope 与 design-{scope} 对齐。

检查摘要文档结构和 `tasks/` 详情文档是否存在。有前端任务时额外确认：`specs/ui-patterns.md` 存在且包含风格基调和 CSS 变量约定；至少一个 `tasks/ui-patterns-{scope}.md` 存在且包含具体 HTML/CSS 代码片段。

## 4. 任务规划

调用 `noah` 创建任务树。要求它使用 `task_writers` 创建阶段父任务和叶子任务，并用 `task_lists()` 自检。编排师再抽查任务标签、父子结构、`task_doc` 关联和可执行粒度。

## 5. 开发实施

循环处理第一个未完成开发 phase：
1. 用 `task_lists()` 找到当前 phase、父任务 ID、未完成叶子任务和技术栈标签。
2. 路由专家：Go -> gavin，Python -> lucas，前端 -> emma，未限定后端语言则根据项目技术栈确定。
3. 一个 phase 只调用一次 `call_agent`：将整个 phase 交给对应专家，指令中给出阶段父任务 ID，由专家在单次会话中完成该 phase 的全部叶子任务。禁止按单个叶子任务逐个调用专家。

> 正例：phase 含 3 个 [Backend:Go] 叶子任务 → 一次 `call_agent(gavin)`，指令：`读取 task_lists(task_id=5, verbose=true) 获取 phase-1 全部任务详情，逐个完成 3 个叶子任务并更新状态。`
> 反例：同一 phase 的 3 个叶子任务 → 调用 gavin 3 次，每次只给 1 个任务。（浪费会话、丢失上下文连贯性）
4. 前端任务指令中额外要求 emma 先读取当前模块对应的 `tasks/ui-patterns-{scope}.md`（scope 根据当前 phase 的模块确定），以其中的代码模式为基准扩展页面。
5. 编排师确认当前 phase 全部完成后，更新阶段父任务状态。

无开发 phase 后进入测试。

## 6. 测试验证

调用 `liam` 执行测试并写入 `tasks/test-report-round-{n}.md`。报告必须包含统计、失败项、技术栈标签、根因和修复建议。

- 全部通过：更新测试阶段状态。
- 有失败：按问题粒度处理，每个失败项独立跟踪修复次数。
  - 该问题修复次数 < 3：按技术栈标签创建修复任务，`task_doc` 指向报告，调用对应专家修复后回归。
  - 该问题修复次数 ≥ 3：标记为"放弃"，记录失败原因和历次尝试。

> 修复计次示例：报告含失败项 A/B/C。A 第 1 次修复通过；B 修复 2 次后通过；C 连续 3 次修复失败 → 标记 C 为"放弃"并记录原因，A/B 正常继续。三者互不影响。
- 所有失败项均已修复或放弃后：更新测试阶段状态，放弃项记入最终报告，继续下一阶段。

### 前端 E2E 验证（有前端任务时必须执行）

开发阶段包含前端任务时，测试验证阶段必须额外调用 `liam` 执行浏览器 E2E 验证，写入 `tasks/test-report-e2e-round-{n}.md`。此步骤独立于后端测试，不可省略。

> E2E 指令示例：`使用 browser_action 验证以下前端页面：1) 登录页表单提交和错误提示 2) 用户列表页数据加载和分页。结果写入 tasks/test-report-e2e-round-1.md，包含每个页面的验证步骤、截图描述和通过/失败状态。`

## 7. 文档撰写

调用 `mia` 编写或更新项目文档。指令中说明：
- 先读取项目 `AGENTS.md`（或已有文档）和工作区 `tasks/` 中对应模块的详情文档，理解项目全貌和本次变更。
- 全局性内容（技术栈、目录结构、模块职责、配置说明、部署方式等所有会话都需要知道的信息）写入或更新项目根 `AGENTS.md`。
- 详细内容（API 文档、模块说明、使用指南、变更说明等）写入项目 `docs/` 目录。
- 在 `AGENTS.md` 的文档清单中为每个 `docs/` 文件添加一行描述和文件名，供后续 LLM 按需读取。
- 项目文档的目的是帮助后续 LLM 在新任务中快速理解项目（区别于工作区文档服务当前任务）。

门控检查：`AGENTS.md` 可读且包含文档清单；清单中列出的 `docs/` 文件路径可读。

## 8. 代码审查

调用 `alex` 审查安全、质量、性能和规范符合度，写入 `tasks/review-round-{n}.md`。

- 无严重/警告问题：更新审查阶段状态。
- 有严重/警告：按问题粒度处理，每个问题独立跟踪修复次数。
  - 该问题修复次数 < 3：按标签创建修复任务，调用对应专家修复后复审。
  - 该问题修复次数 ≥ 3：标记为"放弃"，记录原因和历次尝试。
- 所有问题均已修复或放弃后：更新审查阶段状态，放弃项记入最终报告，继续下一阶段。

## 9. 完成汇报

直接向用户汇报：已实现功能、测试结果、文档路径、审查结论、遗留问题。只引用已验证的产物和状态。
