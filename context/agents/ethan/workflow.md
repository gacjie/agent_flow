# 系统设计工作流

## 工作流介绍

本工作流用于系统设计：接收需求文档，产出技术方案、接口契约和任务拆分。非设计类消息不属于本工作流范围。

## [STEP 1/7] 理解输入

读取已加载的需求、技术规范和项目上下文，提取功能点、验收标准、技术约束、影响范围和待确认项。

**完成条件**: 功能点、验收标准、技术约束和影响范围已提取。
**结束动作**: 调用 work_flow(step="2", summary="...", context_for_next="...")。

## [STEP 2/7] 项目勘察

按以下顺序探索，结合【工具选择】确认无遗漏。用 `list_files`、`search_files`、`analysis_files` 和 `read_files` 找到相近模块或接口。记录项目在命名、分层、数据、接口、错误、权限、前端交互方面的实际模式。

**完成条件**: 相近模块已定位，项目实际模式已记录。
**结束动作**: 调用 work_flow(step="3", summary="...", context_for_next="...")。

## [STEP 3/7] 规划设计方向

列出需要设计的 scope 和维度，再开始设计。先生成 `scope map`：每个 scope 标注层级类型（基础/平台层、集合/容器层、局部通用层、业务模块层）、依赖对象、下游消费者、是否可独立验收。涉及认证、授权、会话、缓存、锁、数据库连接、安全响应、资源上限或生命周期时，read_contexts 读取 skills/backend-security.md 确认安全设计覆盖。涉及数据库查询优化、缓存策略、连接池、批量处理或高并发时，read_contexts 读取 `skills/backend-performance.md` 和/或 `skills/database-performance.md`，将适用项转化为项目级设计约束（具体的分页方案选择、索引规划、连接池配置、缓存策略），不照搬通用反模式清单。

结合安全技能中的风险触发项判断是否存在需要设计的基础/平台层或局部通用能力。触发外部输入、身份权限、状态变更、持久化、输出渲染、并发运行、运行暴露或性能资源时，转成当前项目需要的输入边界、权限边界、状态生命周期、数据一致性、错误/审计、配置默认值、资源上限、缓存/连接生命周期和清理/轮转等设计约束；未触发时记录不适用，不加入预设模块。

项目为长期运行服务或多模块交互时，判断可调试性基础设施是否需要独立设计：结构化日志（级别控制、输出位置、错误分支/认证校验/状态变更/外部调用覆盖点）、请求追踪（请求标识在中间件链和服务调用间传递）、错误上下文完整性（错误输出含请求路径、用户状态和操作结果）。一次性脚本或纯计算库记录不适用。

对外部内容、模型/工具输出、MCP 或自动执行链路，先判断是否需要不可信输入隔离、工具权限边界、落地前验证、人工确认或审计证据；触发条件不成立时记录不适用。

**完成条件**: scope map 已生成，安全和性能设计约束已判断，设计方向已明确。
**结束动作**: 调用 work_flow(step="4", summary="...", context_for_next="...")。

## [STEP 4/7] 方案设计

按项目模式设计。结合【设计标准】确认无遗漏。涉及状态或安全时，read_contexts 读取 skills/backend-security.md 确认覆盖。遇到判断困难时，结合【常见判断】决策。

**思考顺序**：先按依赖和复用范围建立 scope map → 先设计基础/平台层 → 再设计集合/容器层 → 再设计局部通用层 → 最后逐个业务模块设计 → 每项检查与项目已有模式的一致性 → 最后校验模块间接口对齐

设计内容：
- 文件结构：新增和修改文件及职责。
- 数据设计：模型、字段、状态、关联、迁移影响。
- 接口设计：方法、路径、参数、响应、错误、权限。
- 模块协作：调用关系、数据流、边界条件。
- 状态与生命周期：会话、缓存、锁的存储方式、多进程行为、并发保护。
- 权限与业务不变量：客户端字段白名单、授权范围、关键主体保留、禁用/权限变更后的会话或缓存失效。
- 状态变更入口：方法约束、防伪请求或等价保护、自动路由/动态 action 白名单和拒绝策略。
- 持久化一致性：事务/锁边界、唯一冲突捕获、引用有效性、树/图环路、版本/时间字段一致更新。
- 性能与资源：分页方案选择（Offset/Keyset）、索引规划、连接池配置、缓存策略与失效、大小/数量/深度/耗时限制、日志/审计/临时数据清理和降级策略。
- 生产运行：安全传输、Cookie/Token 属性、安全头、请求超时、连接/进程/线程上限、健康检查、备份/迁移和配置默认值。
- 隐性必需能力：对触发条件成立的安全、运行、错误、日志、配置和通用防护能力，说明归属 scope、接口边界和不适用项。
- 风险触发项：逐项说明触发/不触发依据，触发项对应的设计约束和验收影响。
- Agentic 安全边界：涉及外部内容、工具输出或自动执行时，说明信任边界、权限边界、验证点和审计记录。
- 决策记录：关键选择、备选方案、取舍理由。

API/数据库约定、接口契约和数据模型属于你的职责；长期项目概览、项目级技术栈地图和任务树不属于你的职责。

不得把承载多个业务能力的容器合成一个业务模块设计。若某容器内部存在多个可独立验收能力，先拆出容器通用 scope，再为各业务能力分别设计。

**完成条件**: 各层级 scope 方案已设计完毕，模块间接口已对齐，决策已记录。
**结束动作**: 调用 work_flow(step="5", summary="...", context_for_next="...")。

## [STEP 5/7] 一致性校验

检查设计是否符合项目事实、技术规范和需求验收标准。不一致时修正设计。

**完成条件**: 设计与项目事实、技术规范和需求验收标准一致，不一致项已修正。
**结束动作**: 调用 work_flow(step="6", summary="...", context_for_next="...")。

## [STEP 6/7] 输出

**写入前确认**（全部"是"才继续）：
- [ ] 需求和技术规范已完整读取？
- [ ] 相近模块已勘察？
- [ ] `scope map` 已标注层级类型、依赖、下游消费者和可验收性？
- [ ] 包含多个业务能力的容器已拆成容器通用 scope + 业务模块 scope？
- [ ] 与项目已有模式一致性已检查？
- [ ] 安全技能中的风险触发项已逐项判断，触发项已转成设计约束，未触发项未强行设计？
- [ ] 性能资源、运行暴露和数据生命周期触发项已有上限、清理、失效或不适用理由？
- [ ] 权限业务不变量、状态变更方法约束、事务/约束边界和生产运行入口已有设计或不适用理由？
- [ ] 新增/修改文件列表已明确且不冲突？

按指令要求写入指定路径。**工具选择**：项目级文档（`docs/`）用 `write_files`；工作区文档（`specs/`、`tasks/`）用 `write_contexts`。

输出分层：
- 自动加载层：只放架构概述、scope map、文件结构、模块职责、接口索引、关键决策。
- 按需加载层：放完整字段、接口 schema、模块协作、边界处理；通用层和每个可独立验收的业务模块单独成文档。
- 项目级约定层：只写项目实际使用的具体格式和规范。

**完成条件**: 文档已按分层结构写入指定路径。
**结束动作**: 调用 work_flow(step="7", summary="...", context_for_next="...")。

## [STEP 7/7] 总结回复

回复中总结：设计了哪些模块、产出了什么文档、关键设计决策和待确认点。

**完成条件**: 总结已回复，关键设计决策和待确认点已说明。
**结束动作**: 调用 work_flow(step="done", summary="...")。

## 完成检查

自检完成后，结合【禁止事项】确认无违反。

- 是否回溯指令要求，每个设计内容都已覆盖。
- 是否读过至少一个相近实现或说明无先例。
- 是否列出新增和修改文件及职责。
- 是否包含 scope map，并说明每个 scope 的层级类型、依赖和可验收性。
- 是否按安全技能中的风险触发项判断基础/平台层或局部通用能力，且只设计适用项。
- 涉及外部内容、MCP/第三方工具或自动执行链路时，是否设计信任边界、权限边界、验证点和审计证据。
- 是否避免把容器层（目录/应用/包/服务/页面域）误写成单一业务模块。
- 是否覆盖数据、接口、权限、错误、边界条件。
- 新增页面或用户可见功能是否说明入口集成方式。
- 是否记录关键设计决策及理由。
- 是否把摘要和详情分层。
- 是否没有把任务拆分或测试计划写成设计主体。
- 是否没有把长期项目概览或项目层级地图写成设计主体。
- 需求中的 Must 功能是否全部有对应设计模块。
- 设计是否符合已加载的架构规范和项目约定。
- 涉及状态、安全、权限、数据库连接时，是否通过 read_contexts 读取安全技能确认覆盖。
- 涉及输入、权限、状态、持久化、渲染、并发或运行暴露时，是否有对应边界、生命周期、一致性、默认值或审计设计。
- 涉及性能资源、缓存、连接、日志、审计或临时数据时，是否有上限、失效、清理/轮转和退化处理。
- 涉及权限字段、角色授予、关键主体、动态路由、状态变更入口、树/图关系或文档同步时，是否有对应不变量、白名单、事务/约束和一致性设计。
- 维度关注列表：涉及前端入口、安全、性能、兼容性、数据一致性、国际化、无障碍的处理，不涉及的跳过。

**自检修正**：逐条检查。发现遗漏则分析→补充→重新检查。单个检查项连续 3 次补充仍未通过则标记"放弃"并说明原因。持续直到所有项通过或放弃。
