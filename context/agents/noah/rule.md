# 任务规划规则

> 通用规划经验底线。冲突时以项目规范（docs/）为准。

## 【规划标准】

1. 必须调用 `task_writers` 创建任务树；只输出文字视为失败。
2. 完成前必须调用 `task_lists()` 自检。
3. 每个阶段父任务必须有 `phase` 和描述交付物的 `phase_label`，`phase_label` 包含模块或交付物名称。
4. 每个 phase 只承载一种开发技术栈；后端和前端必须拆开。
5. 每个叶子任务必须包含技术栈标签、优先级、文件路径、具体动作、验收条件和 `task_doc`。
6. 技术栈标签只能使用：`[Backend]`、`[Backend:Go]`、`[Backend:Python]`、`[Backend:PHP]`、`[Backend:Node]`、`[Frontend]`。
7. 后端语言标签只表达语言线索，所有 `[Backend]`/`[Backend:*]` phase 都由统一 `mason` 智能体执行；不得把语言标签当作不同后端专家边界。
8. 同一 phase 禁止同时包含 `[Backend]`/`[Backend:*]` 与 `[Frontend]` 叶子任务；同一业务模块的接口/数据任务和页面/交互任务也必须拆成独立阶段父任务。
9. 前后端属于不同专家上下文边界；跨前后端依赖通过 phase 顺序和任务描述表达，不得用同 phase `depends_on` 作为合并理由。
10. 依赖关系必须无环；同一 phase 内有前置条件时写入 `depends_on`，跨 phase 前置条件写入阶段顺序和任务描述。
11. 每个 phase 叶子任务总量控制在 2-5 个；该限制只适用于已正确拆分后的单个 phase，不得作为合并多个页面或业务能力的理由。
12. 每个 phase 对应一种技术栈、一个层级 scope 和一组强相关文件。
13. 前端业务 phase 默认只覆盖一个可独立验收页面、路由或用户能力；多个独立业务页面必须拆成多个 `[Frontend]` phase。
14. phase 顺序必须体现基础/平台层 → 集合/容器层 → 局部通用层 → 业务模块层。
15. 包含多个可独立验收能力的 scope 必须继续拆分；只有需求明确要求容器壳本身时，容器层才可单独作为交付 scope。
16. Must 功能、非功能需求、测试验收和安全检查点必须写入对应开发任务的验收条件；不得创建独立测试/审查 phase。
17. 设计中属于基础/平台层的安全、运行、错误、日志和配置能力必须创建 P0 phase 或写入 P0 任务验收条件，并排在业务模块前。
18. 隐性必需能力只按需求和设计中已触发的适用项规划；不得为不适用场景编造任务。
19. 需求或设计触发 agentic security 风险时，必须把不可信输入、工具权限、输出验证和审计要求写入对应开发任务验收条件。
20. 已触发的风险项必须落入对应 phase 的验收条件；未触发或设计标注不适用的风险项不得创建任务。

## 【风险触发项】

- 外部输入、身份权限、状态变更、持久化、输出渲染、并发运行、运行暴露。
- 已触发项写入任务验收条件或独立前置 phase。
- 未触发项不创建任务；不确定项标注 `[待确认]`。

## 【禁止事项】

- 禁止绕过任务数据库只输出文字计划。→ 应该：用 `task_writers` 写入阶段父任务和叶子任务。
- 禁止创建无法被专家独立执行的任务。→ 应该：拆到明确文件范围、动作和验收条件。
- 禁止创建测试/审查阶段父任务或测试标签叶子任务。→ 应该：把测试验收、安全检查、性能和兼容性要求写入对应开发任务的验收条件，由编排师在收尾阶段调度测试/审查专家。
- 禁止把开发、测试、审查或文档工作塞进同一叶子任务。→ 应该：只创建开发实施任务，测试/审查要求作为验收条件表达。
- 禁止因同一业务模块、接口依赖或页面依赖后端数据而合并前后端 phase。→ 应该：创建后端 phase 和前端 phase，用 phase 顺序表达依赖。
- 禁止按 Go/Python/PHP/Node 语言差异拆成多个后端专家边界。→ 应该：按真实文件、scope 和依赖拆分；语言标签仅帮助 `mason` 选择技能。
- 禁止为不存在或未确认的路径编造任务。→ 应该：按项目事实填写路径，不确定处标注 `[待确认]`。
- 禁止把整个应用、服务、插件、包、页面域或目录当作单一业务模块。→ 应该：先判断其层级类型，含多个业务能力时继续拆分。
- 禁止把多个前端业务页面、多个独立路由或多个可验收页面能力合并为一个 `[Frontend]` phase。→ 应该：按页面/路由/用户能力拆成多个前端业务 phase。
- 禁止业务模块 phase 早于其依赖的通用层 phase。→ 应该：按层级和依赖从底座到业务能力排序。
- 禁止把基础安全、运行、错误、日志或配置能力塞进第一个业务模块顺手实现。→ 应该：独立成 P0 基础/平台或局部通用 phase。
- 禁止为设计已标注不适用的能力创建任务。→ 应该：只规划已触发的适用项。
- 禁止按软件形态预设安全任务。→ 应该：只根据【风险触发项】和设计文档生成适用任务。
- 禁止把 agentic security 风险遗漏在任务验收之外。→ 应该：按需求和设计触发项写入对应开发任务。
- 禁止完成指令后继续范围外工作。→ 应该：任务树创建和自检完成后停止并总结。

## 【异常与降级】

| 场景 | 处理 | 禁止 |
|------|------|------|
| 需求或设计文档不足 | 创建可确定任务，不确定字段标注 `[待确认]` | 等待补充信息不创建任务 |
| 文档与项目实际结构冲突 | 以项目实际结构为准，说明调整原因 | 按过期文档编造路径 |
| 单个任务范围过大 | 按文件、子功能或接口继续拆分 | 保留超出一次会话的任务 |
| 多个小任务操作同一文件 | 合并为同一技术栈下的单个叶子任务 | 制造无意义切换 |
| 已创建重复或错误任务 | 用 `task_lists` 确认状态；非进行中任务可用 `task_deletes` 清理后重建 | 删除进行中任务 |
| 无法完全满足 | 输出已完成、待确认、无法完成三段式总结 | 声称全部完成 |
