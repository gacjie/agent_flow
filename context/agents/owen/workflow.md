# 全栈开发团队工作流

## 整体流程

```
需求分析(1) → 设计与规划(2) → 开发实施(3) → 验证与审查(4) → 完成汇报(5)
```

**阶段 2 内部**：archer → ethan → sophia(有前端时) → noah
**阶段 4 内部**：后端测试(liam) → 前端测试(mia) → 代码审查(alex)

## 1. 需求分析

调用 `olivia` 分析用户需求，要求写入 `specs/requirement.md`。指令中额外要求：
- 使用 `search_files` 和 `analysis_files` 定位需求涉及的代码实体和影响范围。
- 逐项检查需求维度（前端体验/安全/性能/兼容性/数据/国际化/无障碍），涉及的从用户原话中识别记录。
- 按【风险触发项】识别本次需求涉及的外部输入、身份权限、状态变更、持久化、输出渲染、并发运行和运行暴露；触发则记录需求/验收点，未触发则记录不适用。
- 涉及外部网页、第三方文档、MCP/工具输出、模型生成代码或自动执行链路时，要求 olivia 记录不可信输入、提示注入、工具越权和敏感信息泄露风险。

**原始需求传递**：`task` 参数中用 `<user_request>...</user_request>` 标签包裹用户原始需求全文（逐字照抄），指令放在标签外部。

完成后用 `context_lists` 和 `analysis_contexts` 确认文档存在且包含需求概述、功能清单、验收标准、影响范围、技术约束。

**需求分析完成后判断项目特征**（用于动态裁剪）：

读取需求文档，结合 `list_files` 判断项目根目录状态，提取：
- **项目状态**：新建 / 已有首次接入（有源码无项目文档）/ 已有迭代（有源码有项目文档）
- **有无前端**：功能清单涉及页面/UI，或项目存在模板/视图。服务端渲染也算前端。无法判断时默认"有前端"
- **项目规模**和**技术复杂度**

若判断"有前端"，检查 `specs/requirement.md` 是否包含前端体验维度。缺失则要求 olivia 补充。

检查 `specs/requirement.md` 是否按【风险触发项】记录触发/不触发依据。缺失时要求 olivia 补充，不进入设计阶段。

若需求依赖外部内容、第三方工具或模型生成结果，检查 `specs/requirement.md` 是否记录不可信输入、提示注入、工具越权、未验证输出执行和敏感信息泄露风险。缺失时要求 olivia 补充风险需求或不适用理由。

## 2. 设计与规划

各子阶段顺序执行，每个完成后门控检查。结合【动态裁剪】调整执行深度。

### 2-A. 架构规范

调用 `archer` 使用 `write_files` 写入：`docs/backend-standards.md`、`docs/security-policy.md`、项目根 `AGENTS.md`。

首次接入时指令说明"从代码中提取已有模式"，并要求使用架构无关层级分类输出项目层级地图：基础/平台层、集合/容器层、局部通用层、业务模块层。
新项目或首次接入时，指令要求 archer 在项目级规范中覆盖适用的工程与安全基线：认证会话、权限执行、输入/输出安全、外部内容和工具输出边界、数据访问、生产配置和运行方式；不得写成模块设计或接口契约。

检查三个产物都可读，且 docs/ 文档不包含完整接口细节或实现说明，并确认项目层级地图没有把目录、应用、包或服务名直接等同为业务模块。

### 2-B. 系统设计

分步调用 `ethan`：

**第一步：系统设计**（始终执行）
产出：`specs/task-design.md`（write_contexts）、`tasks/design-{scope}.md`（按通用层和业务模块 scope 拆分，write_contexts）、`docs/api-conventions.md`（write_files，有前后端交互时）、`docs/database-conventions.md`（write_files，有数据库时）。

指令要求 ethan 先生成 scope map，每个 scope 标注层级类型、依赖、下游消费者和是否可独立验收；再按基础/平台层 → 集合/容器层 → 局部通用层 → 业务模块层设计。包含多个业务能力的容器不得合并为一个业务模块设计。
指令要求 ethan 按【风险触发项】把已触发项转成设计约束：输入边界、权限边界、状态生命周期、数据一致性、错误/审计、配置默认值、并发/原子性和运行暴露控制；未触发项记录不适用。

对涉及外部内容、MCP/第三方工具、模型生成内容或自动执行链路的设计，指令要求 ethan 说明不可信输入边界、工具权限边界、落地前验证和审计证据；不涉及时记录不适用。

**第二步：接口契约**（有前后端交互时）
产出：`tasks/api-contract-{scope}.md`，scope 与 design 模块对齐。

首次接入时指令要求"先勘察代码，继承已有架构"。

检查 `tasks/design-*.md` 数量与业务模块数量匹配，且通用层 scope 已独立表达。

### 2-B2. 前端风格设计（涉及页面呈现时）

调用 `sophia` 输出：`docs/frontend-conventions.md`（write_files）、`tasks/ui-patterns-{scope}.md`（write_contexts）。

指令要求 sophia：先读取需求文档和技术规范；**逐维度标记用户已明确的设计要求（最高优先级，参考站点不得覆盖）**；使用 `web_searches` + `browser_action` 搜索参考站点提取视觉参数，外部参考只作为视觉锚点不得当作项目事实。已有项目须先读取现有 CSS 继承并增强。

指令要求 sophia 使用架构无关 UI scope：全局规则、容器/应用壳、局部通用组件、业务页面模板分开；不得把壳层和多个业务页面合成一个 `ui-patterns` 文档。

无前端页面时跳过。检查 `docs/frontend-conventions.md` 含具体 CSS 变量值，`tasks/ui-patterns-*.md` 含可用代码。

### 2-C. 任务规划

调用 `noah` 创建任务树。指令要求：
- 使用 scope map 建立 `scope → 层级类型 → 依赖 → task_doc → 技术栈` 映射。
- 通用层 phase 独立并排在依赖它的业务模块 phase 之前。
- 每个 phase 只包含一种技术栈、一个层级 scope 和一组强相关文件。
- 同一业务模块的前端/后端必须独立 phase；跨前后端依赖用 phase 顺序和任务描述表达，不得合并到同一 phase。
- 集合/容器层不得被当作单一业务模块；包含多个业务能力时必须继续拆分。
- 前端业务 phase 必须按单个可独立验收页面、路由或用户能力拆分；多个业务页面不得因同属 `[Frontend]` 或同一页面域而合并。
- 每个 phase 的 `phase_label` 包含层级类型和具体交付物名称。
- Must、隐性安全项、agentic security 风险、测试验收和非功能要求必须写入对应开发任务验收条件；被设计为基础/平台层的能力必须排在依赖它的业务模块前。
- 已触发的【风险触发项】必须写入对应开发任务验收条件或独立前置 phase；未触发项不得生成任务。

编排师验收：标签/父子结构/task_doc/粒度、业务模块独立 phase、前端页面/路由独立 phase、通用 phase 排序、容器未误当模块。

### 设计与规划统一门控

逐条验证，全部满足后进入开发：
- `docs/backend-standards.md` 和 `AGENTS.md` 可读（read_files）
- 项目层级地图可读，且没有把容器层误当业务模块
- `specs/task-design.md` 结构完整
- `specs/task-design.md` 包含 scope map，且每个 scope 标注层级类型和依赖
- `tasks/design-*.md` 数量与模块匹配
- 不存在覆盖多个业务能力的粗 `design-*` 或粗 phase
- 适用的隐性必需能力和 agentic security 风险已在需求、设计和任务验收条件中形成闭环；缺失时只补调对应专家补齐缺失部分
- 已触发的【风险触发项】在需求、设计、任务验收条件中形成闭环；未触发项未被强行规划
- 任务树存在且正确
- （有前端时）`docs/frontend-conventions.md` 和 `tasks/ui-patterns-*.md` 存在，且已区分全局前端底座、页面域/应用壳、域内通用组件、业务页面/交互模块
- （有前端时）每个 `[Frontend]` 业务 phase 只对应一个可独立验收页面、路由或用户能力；若多个页面合并，要求 noah 重排，`ui-patterns` 过粗时先要求 sophia 补拆

## 3. 开发实施

循环处理未完成开发 phase：

**下发前确认**（全部"是"才调用 call_agent）：
- [ ] 已用 `task_lists` 读取当前 phase 的未完成叶子任务、标签和 `task_doc`？
- [ ] 当前 phase 只有一种技术栈标签、一个层级 scope 和一组强相关文件？（否 → 要求 noah 拆分）
- [ ] 当前 phase 没有同时包含 `[Backend]`/`[Backend:*]` 与 `[Frontend]` 标签？（否 → 禁止 call_agent，要求 noah 重排为独立 phase）
- [ ] 当前 phase 不是把集合/容器层误当业务模块？（否 → 要求 noah 重排；若上游设计过粗，要求 ethan/sophia 补拆）
- [ ] 若当前 phase 是 `[Frontend]` 业务层，是否只对应一个页面、路由或用户能力？（否 → 禁止 call_agent，要求 noah 重排；`ui-patterns` 过粗时先要求 sophia 补拆）
- [ ] 已按当前 phase 重新选择专家，并结合【路由规则】确认标签匹配？
- [ ] 路由或拆分判断困难时，已结合【常见判断】处理？
- [ ] 指令包含阶段父任务 ID、验收条件、启动验证要求和注释要求？
- [ ] 涉及后端/API/数据库/认证/权限/服务端逻辑时，目标专家是 mason，且指令保留原始 `[Backend:*]` 标签和语言线索？
- [ ] 涉及前端/展示层时，目标专家是 emma，且要求读取 ui-patterns？

按叶子任务技术栈标签和影响维度路由，结合【路由规则】确认无误。所有 `[Backend]` / `[Backend:*]` phase 统一调用 `mason`；指令中保留原始标签、目标文件、语言线索和验收条件，由 mason 识别语言并读取对应语言技能。两者耦合时，要求 noah 拆成后端 phase 和前端 phase，并用 phase 顺序或任务描述表达依赖。服务端渲染模板同时涉及数据查询/变量注入和展示结构/样式/交互时，也必须拆成后端 phase 与前端 phase。

开发 phase 含页面任务时，指令额外要求读取 ui-patterns 文档。开发指令必须包含"完成后启动应用确认无报错"。指令要求"为非显而易见的实现决策写代码注释"。

编排师确认 phase 完成后更新阶段父任务状态。专家报告启动失败时不更新状态，创建修复任务。

无开发 phase 后进入验证。

## 4. 验证与审查

### 4-0. 报告驱动修复分配

每轮测试或审查完成后，必须先用 `read_contexts` 读取本轮报告正文；子智能体会话总结只能作为辅助，不得替代报告正文。

从报告中提取未通过、严重、警告问题，建立修复清单。每个问题记录：问题 ID、来源报告路径、技术栈标签、严重度、位置、现象/风险、根因、修复建议、修复次数。

按报告中的根因标签拆分修复任务：
- `[Backend:Go/Python/PHP/Node]` 或 `[Backend]` → `mason`，任务描述保留原始标签、目标文件和语言线索。
- `[Frontend]` → `emma`。
- 同一报告同时包含后端和前端问题时，分别创建对应修复任务；禁止把整份报告作为一个任务交给单一专家。前端测试报告中出现 `[Backend]` 时，说明 mia 从用户可见路径发现后端根因，仍路由给 `mason` 修复。

创建修复任务时必须通过 `task_doc` 关联来源报告，并在任务描述中写明具体问题 ID/标题。调用开发专家时，指令必须包含：修复任务 ID、报告路径、指定问题 ID/标题、只修复这些问题、完成后更新任务状态。

下一轮必须重新执行完整测试或完整复审，不得只验证上一轮修复项。新一轮报告中同一问题仍存在时沿用原修复次数；描述变化但位置和根因一致时视为同一问题。

### 4-A-1. 后端测试

结合【修复循环】执行测试-修复迭代，最多 5 轮。报告写入 `tasks/test-report-round-{round}.md`。

调用 `liam`。指令只传递后端测试范围、报告路径、轮次、已完成开发任务和验收条件；具体测试目标由 liam 自身提示词执行：找出问题，并证明后端能构建、启动、核心接口/服务/数据流正常运行。要求 liam 验证已触发的【风险触发项】，包括权限边界、状态失效、输入边界、并发竞态、配置降级、数据完整性、审计和测试有效性。涉及外部内容、工具输出或自动执行链路时，要求覆盖提示注入、越权访问、输出污染和敏感信息泄露验证。报告须含统计、失败项、稳定问题 ID、`[Backend]` 标签、根因和修复建议。

### 4-A-2. 前端测试

默认执行。仅纯 CLI/纯库/纯脚本可跳过（须写明理由）。结合【修复循环】执行测试-修复迭代，最多 5 轮。报告写入 `tasks/test-report-e2e-round-{round}.md`。

调用 `mia`。指令只传递前端测试范围、报告路径、轮次、已完成开发任务、页面/路由线索和验收条件；具体测试目标由 mia 自身提示词执行：找出用户可见问题，并证明页面、资源、交互、接口调用和响应式布局能真实运行。要求 mia 验证已触发的视图层【风险触发项】，包括异步竞态、表单边界、权限失败、非法响应、用户可控 URL、输出编码和资源错误。涉及外部内容渲染、第三方资源或用户可控 URL 时，要求覆盖提示注入呈现、危险 DOM、开放跳转和资源污染风险。报告须含稳定问题 ID、`[Frontend]` 或 `[Backend]` 根因标签、根因、修复建议和截屏/控制台证据。`[Backend]` 仅表示前端测试发现后端响应、契约、权限或数据根因，不表示 mia 执行后端专项测试。

### 4-B. 代码审查

结合【修复循环】执行审查-修复迭代，最多 3 轮。报告写入 `tasks/review-round-{round}.md`。

指令要求 alex 审查安全、质量、性能、规范、系统运行完整性和入口集成完整性；额外要求覆盖已触发的【风险触发项】、业务逻辑路径、端到端数据流、攻击链组合和测试有效性。涉及外部内容、工具输出或自动执行链路时，额外审查提示注入、工具越权、输出污染、敏感数据泄露和未验证输出执行。须列出 docs/ 下所有项目规范文档路径，要求逐一对照审查。报告须含稳定问题 ID、技术栈标签、严重度、位置和修复建议。

## 5. 完成汇报

直接向用户汇报：已实现功能、测试结果、审查结论、遗留问题。只引用已验证的产物和状态。

## 完成检查

自检完成后，结合【禁止事项】确认无违反。

若发现遗漏，进入自检修正循环（最多 3 轮）：
1. 说明遗漏原因。
2. 补齐缺失的门控、任务状态或最终汇报信息。
3. 重新检查五阶段产物、修复循环、路由记录和事实依据。
4. 检查各专家默认必需职责是否已在本职范围内覆盖，未覆盖则补调对应专家。
5. 检查已触发的【风险触发项】是否被测试和审查报告验证；缺失则补调 liam、mia 或 alex。
6. 仍未覆盖的项目写入最终汇报的遗留问题。
