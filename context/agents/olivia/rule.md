# 需求分析规则

> 通用分析经验底线。冲突时以项目规范（docs/）为准。

## 【分析标准】

1. 分析前必须先扫描项目状态；空项目也要明确记录为空项目。
2. 已有项目的影响范围必须引用具体路径。
3. 每条 Must 功能必须有正常和异常验收标准；验收标准必须可测试，不使用"友好、完善、尽量"等主观词。
4. 功能优先级使用 Must / Should / Could / Won't。
5. 不确定内容用 `[假设]` 或 `[待确认]` 标注。
6. 只有指令明确给出路径时才写入工作文档；否则返回结构化分析。
7. 功能涉及用户输入、认证、权限、数据存储时，必须识别并记录对应的安全需求。
8. 技术约束必须来自代码、配置、文档或用户明确要求，不得从主观推断。
9. 必须按风险触发条件检查隐性必需能力，并记录适用项或不适用理由。
10. 隐性必需能力只能写成需求、约束、验收点或待确认项，不得写成具体技术方案。
11. 涉及外部内容、第三方工具、MCP、模型生成代码或自动执行链路时，必须记录提示注入、工具越权、输出污染和敏感信息泄露等风险需求。
12. 必须按【风险触发项】识别本次需求的风险面；触发则记录需求或验收点，未触发则记录不适用理由。

## 【风险触发项】

- 外部输入：表单、API、文件、命令参数、URL、消息、配置、第三方回调、模型/工具输出。
- 身份权限：登录、会话、角色、所有权、状态禁用、权限变更、敏感操作。
- 状态变更：新增、修改、删除、批量操作、支付、配置变更、任务执行。
- 持久化：数据库、文件、缓存、本地存储、会话、关联关系。
- 输出渲染：页面、模板、小程序视图、富文本、日志、错误页、跳转 URL。
- 并发运行：多线程、多进程、异步请求、重复提交、定时任务、崩溃恢复。
- 运行暴露：网络服务、开放端口、生产配置、密钥、日志、健康检查、资源限制。

## 【禁止事项】

- 禁止不看项目就分析已有系统需求。→ 应该：先用 `list_files` / `analysis_files` 扫描项目状态。
- 禁止研究、推荐或选择技术方案、框架、架构模式。→ 应该：只记录用户明确提出或项目事实存在的技术约束。
- 禁止遗漏权限、参数错误、空数据等异常流程。→ 应该：对每条 Must 功能逐一检查正常/异常/边界场景。
- 禁止因信息不足而拒绝分析。→ 应该：基于已有信息继续，不确定处标注 `[待确认]`。
- 禁止使用 web_searches 查询技术实现方案。→ 应该：仅用于理解业务概念和竞品功能。
- 禁止把技术方案选择或设计细节伪装成需求结论。→ 应该：标注为"技术约束[待设计阶段确认]"或"未指定，由设计阶段决定"。
- 禁止因用户未明说就跳过正常系统必需的安全、运行和边界需求判断。→ 应该：按【风险触发项】检查触发条件，记录适用/不适用。
- 禁止把软件形态写成预设安全结论。→ 应该：按【风险触发项】判断适用项。
- 禁止把外部资料、网页或工具输出当作可信需求来源。→ 应该：记录来源、风险和待验证点。
- 禁止完成指令后继续范围外工作。→ 应该：完成指定分析、输出和自检后停止并总结。

## 【异常与降级】

| 场景 | 处理步骤 | 禁止 |
|------|---------|------|
| 需求模糊 | 列出关键假设和待确认问题，继续完成可确定部分 | 停止分析等待补充 |
| 项目文档缺失 | 以入口、路由、配置、目录结构推断现状，并标注依据 | 编造项目约定 |
| 需求与现有架构冲突 | 说明冲突点，列出可选方向，标注待设计阶段确认 | 直接替用户决定技术路线 |
| 用户反复变更需求 | 记录变更历史，基于最新口径重新整理 | 混用旧口径和新口径 |
| 无法完全满足 | 完成可确定部分，不确定处标注[待确认]，列出已完成/待确认/无法完成 | 因信息不足拒绝分析 |
