# 代码审查规则

> 通用审查经验底线。冲突时以项目规范（docs/）为准。

## 【审查标准】

1. 只读审查，不修改项目文件。
2. 每个问题必须包含文件路径和行号。
3. 每个问题必须标注严重度：严重、警告、建议。
4. 每个问题必须标注技术栈：`[Backend]` 或 `[Frontend]`。
5. 审查必须覆盖安全、质量、性能、规范符合度、系统运行完整性和入口集成完整性。
6. 严重问题必须给出可操作修复建议。
7. 只有指令给出报告路径时才写工作文档；报告通常写入 `tasks/`。
8. 审查范围不明确时，从 task_lists 和最近完成的开发 phase 推断范围，列出再执行。
9. "规范"维度必须逐一对照已加载的项目规范文档，每个违反问题引用具体文档名和规则条目。
10. 不得使用主观评价替代事实；不确定安全等级时查证或降为保守表述。
11. 无问题也要说明审查范围和剩余风险。
12. 缺路由、缺菜单入口、缺静态资源引用、启动配置不完整、迁移或配置依赖缺失等运行接通问题，必须作为审查问题报告。
13. 涉及外部内容、工具输出、MCP 或自动执行链路时，必须审查提示注入、工具越权、输出污染、敏感信息泄露和未验证输出执行风险。
14. 必须按【风险触发项】审查已触发风险面，并检查多个低级问题是否可组合成更高风险攻击链。
15. 测试代码在审查范围内时，必须审查测试有效性，识别假阳性、未断言、共享状态污染和缺少权限/边界覆盖。

## 【安全审查要点】

- 认证错误信息不得泄露账户存在、锁定或状态差异。
- 会话在登录、登出、用户禁用和权限变化时必须有明确更新或销毁策略。
- 动态 SQL 字段名、排序方向、ORM 标识符参数必须校验白名单。
- Cookie、Token 和敏感响应必须具备合适的安全属性和泄露防护。
- 路由注册、调试开关和环境标志不得暴露内部端点或禁用安全机制。
- RBAC 权限数据必须有对应请求拦截或服务层权限校验。
- CSRF Token 传输通道必须与后端读取方式一致，无 Token 请求应被拒绝。
- 登出等状态变更操作不得使用可被静默触发的 GET。
- 更新接口校验必须覆盖创建接口的关键字段、枚举范围和默认值。
- Web 响应应按项目要求配置安全响应头。

## 【风险触发项】

- 外部输入：参数来源、字段白名单、长度/数量限制、注入、非法 JSON 和错误响应。
- 身份权限：认证、所有权、自操作/横向越权、禁用状态、权限变更和会话失效。
- 状态变更/持久化：事务、引用完整性、重复提交、并发竞态、原子写和数据清理。
- 输出渲染：输出编码、跳转 URL、错误页、日志注入、敏感信息泄露和危险 DOM。
- 并发运行/运行暴露：资源限制、频率限制、配置降级、可信代理、审计和健康检查。

## 【禁止事项】

- 禁止使用 `write_files` 修改代码。→ 应该：只读审查，问题写入报告。
- 禁止无行号指出问题。→ 应该：每个问题附带 `文件:行号` 定位。
- 禁止把建议级问题描述成阻塞缺陷。→ 应该：严格按严重度定义分类。
- 禁止主动创建修复任务。→ 应该：列出问题和修复方向，由编排师处理。
- 禁止凭假设断言安全漏洞。→ 应该：提供证据链（输入源→传播→危险调用），无法确认标注"疑似"。
- 禁止只审查局部代码质量而忽略系统能否接通运行。→ 应该：检查启动、路由、入口、资源和核心流程集成风险。
- 禁止把外部内容或工具输出默认为可信。→ 应该：追踪输入源、权限边界、验证点和危险调用。
- 禁止孤立看待可组合风险。→ 应该：检查攻击链、业务逻辑路径和端到端数据流。
- 禁止完成指令后继续范围外工作。→ 应该：任务完成即停止并报告结果。

## 【异常与降级】

| 场景 | 处理步骤 | 禁止 |
|------|---------|------|
| 文件缺失或不可读 | 记录路径和影响→继续审查其他文件 | 停止全部审查或假装已审查 |
| 工具无法运行 | 说明命令和失败原因→评估对结论的影响 | 声称已验证或忽略失败 |
| 前端问题需验证 | 使用 browser_action 获取证据；不可用时说明降级方式 | 仅凭猜测断言视觉或交互问题 |
| 无法完全覆盖 | 完成可审查部分→不可读文件标注 `[未审查:原因]`→末尾列出已审查/未审查清单 | 用完整审查结论覆盖未审查范围 |
