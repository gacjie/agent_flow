# 通用全栈开发工作流

## 1. 读取任务

用 `task_lists` 确认当前任务。若提供任务 ID，先读取 `task_lists(task_id=..., verbose=true)`，确认 `task_doc`、验收条件和依赖。

## 2. 识别项目技术栈

扫描项目结构，通过配置文件识别语言和框架：
- `go.mod` → Go
- `package.json` → Node.js/TypeScript
- `pom.xml` / `build.gradle` → Java
- `Cargo.toml` → Rust
- `Gemfile` → Ruby
- `*.csproj` / `*.sln` → C#/.NET
- `composer.json` → PHP
- `requirements.txt` / `pyproject.toml` → Python

读取目标文件、同类实现和公共工具，确认框架、错误处理、数据访问、测试和验证方式。任务涉及页面时，还须读取基础模板和已有同类页面。

勘察完成后，在回复中列出：识别的技术栈、要完成的所有要点、实施顺序和安全关注点，再开始编码。

## 3. 实施变更

按任务逐项编码：
- 优先复用现有函数、模型、配置和依赖。
- 保持接口契约、字段名、状态值和错误格式一致。
- 覆盖输入、异常、安全、权限、资源释放等边界。
- 修复任务只处理关联问题文档中的问题。

## 4. 验证

按以下层次逐步验证，每层通过后再进入下一层：

1. **编译/语法检查**：运行项目对应的编译或语法检查命令。
2. **集成启动**：确认修改的模块能被项目入口正确加载，无报错。
3. **功能可达**：若实现了路由或页面，确认可响应或可渲染。前端页面使用 `browser_action` 验证。
4. **测试通过**：运行项目已有测试命令。

若验证失败，修复后重跑。无法运行时说明具体原因，不得声称"已验证"而未实际执行命令。

## 5. 收尾

更新任务状态。回复中总结：识别的技术栈、完成的要点、修改文件、验证方式、结果和待确认点。

## 完成检查

- 是否正确识别了项目语言和框架。
- 是否回溯指令要求，逐条确认每个要点都已实现。
- 是否检查安全规范：输入校验、参数化查询、权限控制、资源释放均已覆盖。
- 是否读取目标文件、同类实现和公共工具。
- 是否保持接口契约、字段名、错误格式一致。
- 是否运行了编译、启动、测试验证。
- 是否更新任务状态。
- 是否检查了以下开发维度（涉及的处理、不涉及的跳过）：日志与可观测性（关键操作是否有日志）、配置外部化（无硬编码魔法值）、向后兼容性（修改已有接口时）。
