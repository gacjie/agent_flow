# 任务规划工作流

## 工作流介绍

本工作流用于任务规划：接收设计文档，拆分为可执行的开发任务树。非任务规划类消息不属于本工作流范围。

## [STEP 1/5] 读取输入

- 从自动加载的 `specs/` 中提取需求、技术规范、设计摘要。
- 调用 `context_lists(directory="tasks")`，再用 `analysis_contexts` 识别详细设计和接口契约。
- 建立"scope → 层级类型 → 依赖 → task_doc → 技术栈"映射。层级类型包括基础/平台层、集合/容器层、局部通用层、业务模块层。

记录识别到的通用层、容器层、业务模块、技术栈、可用任务文档和待确认缺口。

**完成条件**: 需求和技术规范已提取，scope 映射已建立，待确认缺口已记录。
**结束动作**: 调用 work_flow(step="2", summary="...", context_for_next="...")。

## [STEP 2/5] 勘察项目

按以下顺序探索，结合【工具选择】确认无遗漏。

用 `list_files` 确认相关目录和文件是否存在，判断任务是新增、修改还是扩展。文件路径必须按项目实际结构填写。

**完成条件**: 项目结构已勘察，任务类型（新增/修改/扩展）已判断，文件路径已确认。
**结束动作**: 调用 work_flow(step="3", summary="...", context_for_next="...")。

## [STEP 3/5] 拆分任务

按设计文档规划。结合【任务字段决策】确定标签、优先级、`task_doc` 和依赖。结合【规划标准】确认硬约束无遗漏。遇到边界判断时，结合【常见判断】决策。

**思考顺序**：列出 scope → 标注层级类型 → 映射文档 → 标记 Must/已触发风险项/agentic security 风险/非功能要求 → 按项目类型过滤不适用的安全/性能面 → 按技术栈二次拆分 → 识别依赖 → 划分 phase → 确定文件范围和验收条件 → 准备写入。

按 scope map 拆出叶子任务。先按 scope 拆分，再按技术栈二次拆分 phase。每个 phase 对应一种技术栈 + 一个层级 scope + 一组强相关文件；每个叶子任务只交给一个专家执行，任务字段按【任务字段决策】填写。

同一业务模块同时包含接口/数据和页面/交互时，必须拆成后端 phase 与前端 phase。跨前后端依赖写入 phase 顺序或任务描述，不得为了使用 `depends_on` 把 `[Backend]`/`[Backend:*]` 与 `[Frontend]` 放进同一 phase。

若某 scope 是集合/容器层且包含多个可独立验收能力，必须继续拆分为局部通用层和业务模块层；不得创建"整个应用/服务/插件/页面域"一类粗 phase，除非需求确实只要求容器壳本身。

前端 scope 按全局前端底座 → 页面域/应用壳 → 域内通用组件 → 单个业务页面/交互模块拆分。前端业务页面 phase 可包含该页面自己的布局、局部组件、状态、接口绑定和入口集成，但不得包含多个独立页面、独立路由或可单独验收的页面能力。

设计中已触发的基础/平台层或局部通用安全、运行、错误、日志、配置、性能资源、数据生命周期能力必须成为 P0 phase 或写入对应 P0 任务验收条件，且排在依赖它的业务模块之前。未触发或设计标注不适用的能力不得创建任务。

设计中标记的外部内容、模型/工具输出、MCP 或自动执行链路风险，必须写入对应开发任务验收条件；涉及通用防护时排在依赖业务模块之前。

设计中标记的权限业务不变量、状态变更方法约束、防伪请求、事务/锁/约束兜底、树/图环路、版本/时间一致性、文档同步和测试有效性要求，必须写入对应开发任务验收条件；属于通用基础能力时排在业务模块之前。

**完成条件**: 叶子任务已按 scope 和技术栈拆分完成，标签/优先级/依赖/验收条件已确定。
**结束动作**: 调用 work_flow(step="4", summary="...", context_for_next="...")。

## [STEP 4/5] 组织阶段

选择阶段划分方式，并按依赖排列：

| 划分方式 | 适用场景 | 顺序 |
|------|---------|------|
| 后端优先 | 模块间接口依赖较多 | 基础/平台→集合/容器→局部通用→后端业务模块→前端公共→前端业务模块 |
| 模块交替 | 模块独立性强 | 基础/平台→集合/容器→局部通用→(后端模块A→前端模块A→后端模块B→前端模块B) |
| 单模块增量 | 小范围迭代 | 受影响通用层→后端业务变更→前端业务变更 |

业务模块的标准顺序是：后端业务能力 phase → 前端展示/交互 phase。先排基础/平台层，再排集合/容器层，再排局部通用层，最后排业务模块。测试和审查不进入任务树，由编排师在开发完成后统一调度；相关测试验收、安全、性能和兼容性要求必须写入开发任务验收条件。多模块时按 `tasks/design-{scope}.md` 的 scope 组织阶段，但必须按层级类型校正粗粒度 scope。

**完成条件**: 阶段划分方式已选择，phase 顺序已按层级和依赖排列。
**结束动作**: 调用 work_flow(step="5", summary="...", context_for_next="...")。

## [STEP 5/5] 写入与自检

**创建前确认**（全部"是"才继续）：
- [ ] 设计文档和模块详情已读取？
- [ ] scope map 已覆盖层级类型、依赖、`task_doc` 和技术栈？
- [ ] 阶段顺序已体现基础/平台、集合/容器、局部通用、业务模块的依赖？
- [ ] 每个阶段父任务下的叶子任务技术栈标签同类，且没有混合 `[Backend]`/`[Backend:*]` 与 `[Frontend]`？
- [ ] 前后端依赖已用 phase 顺序或任务描述表达，而不是用同 phase `depends_on` 合并？
- [ ] 集合/容器层没有被误当成单一业务模块？
- [ ] `[Frontend]` 业务 phase 是否只覆盖一个可独立验收页面、路由或用户能力？
- [ ] Must 功能和关键非功能需求已覆盖？
- [ ] 隐性安全、运行性和测试验收要求已进入对应任务或验收条件？
- [ ] 已触发的性能资源、数据生命周期、日志/缓存/连接边界已进入 P0 phase 或对应验收条件？
- [ ] 已触发的权限不变量、方法约束、事务/约束、文档同步和测试有效性要求已进入对应验收条件？
- [ ] 已触发的风险触发项已进入对应任务验收条件，未触发项未生成任务？
- [ ] agentic security 风险已进入对应任务验收条件，且没有被塞进无关任务？
- [ ] 叶子任务字段已包含标签、路径、动作、验收条件和 `task_doc`？
- [ ] 依赖关系可执行且无环？

1. `task_writers` 创建阶段父任务。
2. 记录父任务 ID 后创建叶子任务，设置 `parent_id`、`priority`、`task_doc`、`depends_on`。
3. `task_lists()` 自检父子结构、标签、文档关联、粒度、覆盖范围和状态。
4. 回溯需求和设计文档确认 Must 覆盖，有遗漏则补充。
5. 发现重复或错误任务时，按【异常与降级】处理。
6. 回复总结阶段数量、任务数量、自检结果和待确认点。

**完成条件**: 任务已写入，父子结构和依赖已自检通过，总结已回复。
**结束动作**: 调用 work_flow(step="done", summary="...")。

## 完成检查

自检完成后，结合【禁止事项】确认无违反。

- 覆盖：Must 功能、关键非功能需求、测试验收和安全检查点是否有任务或验收条件。
- 风险：外部内容、工具输出、自动执行链路相关风险是否写入对应任务验收条件。
- 基线：已触发的基础/平台层安全、运行、错误、日志、配置能力是否排在业务模块前，且没有被塞进业务模块顺手实现。
- 性能：已触发的资源上限、清理/归档、缓存/连接生命周期、日志轮转和性能退化验收是否落入任务。
- 一致性：权限不变量、状态变更入口、事务/约束边界、版本/时间字段、文档同步和测试有效性验收是否落入任务。
- 结构：phase 是否按层级和依赖排序，且每个 phase 只含一种技术栈、一个层级 scope、一组强相关文件；任一阶段父任务下不得同时出现 `[Backend]`/`[Backend:*]` 和 `[Frontend]`。
- 粒度：是否存在把目录、应用、包、服务、插件或页面域整体当作业务模块的粗 phase；是否存在把多个前端业务页面、独立路由或可验收页面能力合并到一个 `[Frontend]` phase。
- 字段：叶子任务是否包含标签、优先级、文件路径、动作、验收条件和 `task_doc`。
- 依赖：`depends_on` 是否仅用于同一技术栈、同一 phase 内部依赖；跨前后端依赖是否已用 phase 顺序或任务描述表达；不确定依赖是否已标注 `[待确认]`。
- 前端/验收：新增页面是否关联 `ui-patterns` 并要求集成入口；测试验收、安全、性能和兼容性要求是否写入对应开发任务。
- 禁令：是否存在只输出文字、模糊任务、混合职责或编造路径。

**自检修正**：逐条检查。发现遗漏则分析→补充→重新检查。单个检查项连续 3 次补充仍未通过则标记"放弃"并说明原因。持续直到所有项通过或放弃。
