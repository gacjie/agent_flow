# 代码审查工作流

## 1. 确认范围

读取已加载需求、设计、规范、任务和项目文档。用 `task_lists()` 识别已完成开发任务和重点文件。

在回复中列出本次审查的重点文件和关注维度（安全、质量、性能、规范），再开始扫描。

## 2. 扫描代码

用 `list_files`、`analysis_files`、`read_files`、`search_files` 查看变更范围、同类实现和高风险模式。只读取必要内容，避免无目标全文扫描。

## 3. 多维审查

逐项检查：
- 安全：输入校验、权限、认证、敏感信息、注入、XSS/CSRF、配置风险；安全机制是否被环境/调试标志条件性禁用；认证错误信息是否泄露账户状态差异（如区分"不存在"和"已锁定"）；会话是否在登出和用户禁用时完整销毁；动态 SQL 字段名/排序方向是否校验白名单；Cookie 是否设置 HttpOnly 和安全属性。
- 质量：复杂度、重复、错误处理、命名、边界、可维护性；是否存在跨模块的重复工具函数（同名或同功能）；安全校验函数是否在所有入口点被调用。
- 性能：分页、批量查询、资源释放、缓存和并发风险；是否存在循环内逐条查询（N+1）或逐条提交；共享可变状态是否有并发保护；高频权限检查是否有缓存。
- 规范：项目约定、接口契约、字段、状态值、数据格式。

## 4. 验证与定级

对不确定问题用项目命令、静态检查、搜索或浏览器验证补充证据。按影响和可利用性定为严重、警告或建议。

## 5. 输出

若指令给出路径，写入审查报告。回复必须包含审查范围、问题统计、问题明细、整体结论：通过或需修复。

## 完成检查

- 是否回溯指令要求，确认每个要求审查的维度都已覆盖；若有遗漏则补充。
- 是否明确审查范围和依据。
- 是否覆盖安全、质量、性能、规范四类检查。
- 每个问题是否有路径、行号、标签、严重度。
- 严重或警告问题是否给出修复方向。
- 是否没有修改项目文件或创建修复任务。
- 无问题时是否说明剩余风险和未覆盖范围。
