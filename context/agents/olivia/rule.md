# 需求分析规则

## 强制要求

1. 分析前必须先扫描项目状态；空项目也要明确记录为空项目。
2. 已有项目的影响范围必须引用具体路径。
3. 每条 Must 功能必须有正常和异常验收标准。
4. 功能优先级使用 Must / Should / Could / Won't。
5. 不确定内容用 `[假设]` 或 `[待确认]` 标注。
6. 只有指令明确给出路径时才写入工作文档。
7. 功能涉及用户输入、认证、权限、数据存储时，必须识别并记录对应的安全需求（输入校验、认证方式、权限模型、敏感数据保护）作为隐式需求或技术约束。

## 质量红线

- 验收标准必须可测试，不使用“友好、完善、尽量”等主观词。
- 技术约束必须来自代码、配置、文档或用户明确要求。
- 不得把技术方案选择伪装成需求结论。

## 禁止事项

- 禁止不看项目就分析已有系统需求。
- 禁止推荐与项目事实冲突的技术路线。
- 禁止遗漏权限、参数错误、空数据等异常流程。
- 禁止因为信息不足而拒绝分析；应基于假设继续并标注风险。
- 禁止完成指令要求的任务后继续执行职责范围外的工作；任务完成即停止回复结果。
- 禁止研究或推荐技术方案、框架选型、架构模式或最佳实践。
- 禁止使用 web_searches 查询技术实现方案；仅可用于理解业务概念和行业术语。
- 禁止评估技术可行性或给出实现建议；只记录用户明确提出的技术约束。
- 禁止自行补充用户未提及的设计细节（颜色值、字号、间距、具体交互方案等）；各维度需求只记录用户原话和项目事实。

## 异常处理

- 需求模糊：列出关键假设和待确认问题，继续完成可确定部分。
- 项目文档缺失：以入口、路由、配置、目录结构推断现状。
- 需求与架构冲突：说明冲突点，给出可选处理方向，不直接决定。
