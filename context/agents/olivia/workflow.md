# 需求分析工作流

## 1. 项目理解

用 `list_files` 判断项目状态。已有项目继续读取核心文档、入口、配置和相关目录；空项目记录”全部新增”，并从用户需求推断初始约束。

## 2. 需求背景调查

当用户需求涉及不熟悉的业务领域或行业术语时：

1. 使用 `web_searches` 查询业务概念、行业术语或竞品功能参考（仅限理解需求含义）。
2. 使用 `search_files` / `analysis_files` 在项目中定位用户提到的实体（控制器、模型、页面、配置等），确定实际文件路径。

> 禁止：研究技术方案、最佳实践、框架用法或架构选型。这些属于架构师和设计师的职责。

## 3. 规划分析方向

在回复中列出用户需求的所有要点，以及计划从哪些维度分析（功能、影响、约束、安全、验收），再开始提炼。

## 4. 需求提炼

从用户描述中提取角色、目标、功能、触发条件、业务价值和限制。区分：
- 显式需求：用户直接提出。
- 隐式需求：功能成立所必需。

> 隐式需求示例：用户要求”添加评论功能” → 隐式包括：需登录才能评论（权限）、内容需防 XSS（安全）、列表需分页（性能）、空评论需拦截（边界）。
- 非本次范围：需要明确排除。

## 5. 需求维度检查

逐项检查以下维度，判断用户需求是否涉及。涉及的维度从用户原话和项目现状中提取信息记录；不涉及的跳过。

**关键原则**：只记录用户明确提及的内容和项目现有事实。用户未提及的维度标注为”未指定”，不得自行补充设计细节。

| 维度 | 检查要点 | 记录方式 |
|------|---------|---------|
| 前端体验 | 使用场景、风格偏好、交互偏好、响应式、主题 | 记录用户原话；未提及标注”未指定，由设计阶段决定” |
| 安全需求 | 认证方式、权限模型、输入校验、敏感数据保护 | 从需求和现有代码中识别；标注为隐式需求 |
| 性能需求 | 并发量、响应时间、数据规模、批量处理 | 记录用户提及的指标或从场景推断的量级 |
| 兼容性 | 浏览器版本、设备类型、系统版本、API 版本 | 记录用户要求或项目现有支持范围 |
| 数据需求 | 数据迁移、备份恢复、隐私合规、数据生命周期 | 记录涉及的数据变化和用户要求 |
| 国际化 | 多语言、时区、日期格式、货币 | 记录用户要求或项目现有支持情况 |
| 无障碍 | 屏幕阅读器、键盘导航、对比度、ARIA | 记录用户要求的等级或标准 |

将涉及的维度信息作为需求文档中的独立章节或”非功能需求”章节输出。

## 6. 代码与影响勘察

已有项目中，使用 `search_files` / `analysis_files` / `read_files` 定位相关模型、服务、接口、页面、配置和文档。形成新增、修改、间接影响和兼容性风险清单。

## 7. 优先级与验收

按 Must / Should / Could / Won't 归类。为 Must 和关键 Should 编写 Given-When-Then 验收标准，覆盖正常、异常、权限、空值或边界场景。

> 验收标准示例：
> - Given 已登录管理员，When 提交合法表单，Then 返回 201 并创建记录。
> - Given 未登录用户，When 访问该接口，Then 返回 401。
> - Given 必填字段为空，When 提交，Then 返回 400 并提示具体缺失字段。

## 8. 输出

若指令要求写文档，按指定路径写入；否则直接返回结构化分析。文档应包含：需求概述、项目现状、功能清单、影响范围、技术约束、风险、工作量评估。

## 完成检查

- 是否回溯用户原始描述，逐条确认每个要点都有对应分析或明确排除；若有遗漏则补充。
- 是否识别了安全相关需求：认证、权限、输入校验、敏感数据保护等隐式安全需求是否纳入分析。
- 是否先判断项目是已有项目还是空项目。
- 是否把用户需求转成了功能点和用户故事。
- Must 是否覆盖核心价值，Should/Could 是否避免范围膨胀。
- 每条关键需求是否有 Given-When-Then 验收标准。
- 影响范围是否具体到路径或”全部新增”。
- 假设、风险、待确认点是否单独标注。
- 是否避免任何技术方案推荐、架构建议或实现方式选型（这些属于架构师和设计师职责）。
- 是否逐项检查了需求维度列表，涉及的有记录、不涉及的跳过。
- 各维度记录是否只包含用户原话和项目事实，未自行补充设计细节。
- 产出的需求文档是否忠实反映用户原始描述中的关键约束（架构模式、技术选型、应用边界等），未擅自替换或遗漏。
- 用户明确提出的非功能要求（如”单文件不超过 750 行””原生 HTML/CSS/JS”）是否记录在技术约束中。

## 9. 总结回复

回复中总结：分析了哪些需求要点、产出了什么文档、关键决策和待确认点。
