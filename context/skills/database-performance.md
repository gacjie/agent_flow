# 数据库性能优化技能

> 数据库性能优化全面清单。设计师读取后按项目裁剪产出数据库约定——选择分页方案、索引策略、连接池配置等。开发者按需读取优化查询和解决性能问题。

## 一、索引策略

### 复合索引列序原则

1. 等值条件列放前面
2. 范围条件列放后面
3. 高选择性列靠前

### 最左前缀规则

复合索引 `(country, city, age)` 可支持：
- 全部三列匹配 -- 命中
- `country` 单列 -- 命中
- `country + city` -- 命中
- 跳过 `country` 直接用 `city` 或 `age` -- **不命中**

### 索引类型

| 类型 | 说明 | 适用场景 |
|------|------|---------|
| 覆盖索引 | 包含查询所需全部列，消除回表 | 读密集型高频查询 |
| 部分索引 | 只索引常用条件（如只索引活跃用户） | 过滤条件固定的场景 |
| 唯一索引 | 强制唯一约束 + 加速查找 | 业务主键、唯一标识 |
| 全文索引 | 文本搜索优化 | 搜索功能 |

### 索引反模式

| 反模式 | 问题 | 正确做法 |
|--------|------|---------|
| 无索引全表扫描 | 大表查询极慢 | 为 WHERE/JOIN/ORDER BY 列建索引 |
| 过度索引 | 拖慢 INSERT/UPDATE/DELETE | 只建必要索引，定期清理未用索引 |
| 低选择性列索引 | status 仅 3 种值，索引效果差 | 结合高选择性列建复合索引 |
| 冗余重复索引 | 浪费存储和写入性能 | 合并或删除重复索引 |
| 索引膨胀未维护 | 索引体积过大、效率下降 | 定期重建膨胀索引 |

### Index Seek vs Index Scan

- **Index Seek**：B-Tree 直接定位目标行（高效，O(log n)）
- **Index Scan**：遍历整个索引（较慢，O(n)）
- 大数据集过滤必须确保使用 Seek，Scan 说明索引设计不当

### 索引维护

- 定期检查未使用/重复/膨胀索引
- 在类生产数据量上测试索引变更（小数据量测试结果不可靠）
- 监控索引使用统计，清理写入成本高但从未被查询命中的索引

## 二、查询优化

### 慢查询诊断

- EXPLAIN / EXPLAIN ANALYZE 查看执行计划
- 关注全表扫描（MySQL type=ALL / PostgreSQL Seq Scan）
- 关注占总 DB 时间 >5% 的查询（最高投入产出比）
- 工具：慢查询日志（MySQL `slow_query_log`、PostgreSQL `pg_stat_statements`）

### 优化技术（按投入产出比排序）

| 优先级 | 技术 | 说明 |
|--------|------|------|
| 1 | 建立合理索引 | 覆盖 WHERE/ON/ORDER BY/GROUP BY 列 |
| 2 | 避免 SELECT * | 只选需要的列，减少 I/O 和内存 |
| 3 | 避免 WHERE 函数 | `WHERE YEAR(date)=2023` 改为 `WHERE date BETWEEN ...` |
| 4 | 限制返回行数 | WHERE 过滤 + LIMIT，避免返回不需要的数据 |
| 5 | 优化 JOIN | 索引 JOIN 列、合适 JOIN 类型、JOIN 替代子查询 |
| 6 | 表分区 | 大表按时间/范围分区减少扫描量 |
| 7 | 更新统计信息 | 帮助优化器做出正确执行计划决策 |
| 8 | 分批处理 | 大 INSERT/UPDATE 拆小批次减少锁持有时间 |

### 性能影响

> 设计良好的索引策略可将 30 秒查询变为 30 毫秒。先测量再优化——确定瓶颈所在，避免过度微优化低频查询。

## 三、分页方案

### Offset 分页

```sql
SELECT * FROM orders ORDER BY id LIMIT 20 OFFSET 1000;
```

| 特性 | 说明 |
|------|------|
| 性能 | O(n) 退化——OFFSET 99980 可能 8 秒 |
| 一致性 | 行插入/删除导致重复或遗漏 |
| 优势 | 支持随机页访问、实现简单、ORM 原生支持 |
| 适用 | <10000 条、静态数据、需页码导航的管理后台 |

### Keyset/Cursor 分页

```sql
SELECT * FROM orders
WHERE (created_at, id) > ('2024-01-15 10:30:00', 1234)
ORDER BY created_at ASC, id ASC
LIMIT 20;
```

| 特性 | 说明 |
|------|------|
| 性能 | O(1) 恒定——无论数据集多大性能一致 |
| 一致性 | 不会重复/遗漏 |
| 限制 | 不支持随机页访问、实现复杂度更高 |
| 适用 | 大数据集、动态数据、API、信息流、ETL 扫描 |

### 实践建议

- 管理后台用 Offset（简单直观，数据量通常可控）
- API 和大数据集用 Keyset（性能保障）
- 复合 cursor `(updated_at, id)` 确保唯一排序
- 创建匹配 keyset 排序顺序的复合索引
- OFFSET > 10000 作为警戒线考虑切换

## 四、连接池管理

### 池配置

| 参数 | 建议 | 说明 |
|------|------|------|
| 池大小 | 每节点 8-16 起步 | 压测确认最优值，预留 25% 容量 |
| 等待超时 | 3-5s | 避免无限阻塞 |
| 空闲超时 | 按场景配置 | 回收不用连接释放 DB 资源 |
| 最大生命周期 | 30min-1h | 防连接老化、DNS 变更 |
| 验证 SQL | `SELECT 1` | 确保连接健康可用 |

### 隔离与监控

- API 和后台任务使用**独立连接池**，防止混合负载竞争
- 读写分离场景配置读池和写池
- 连接泄漏告警（借出未归还）
- 池利用率 >80% 需扩容或优化查询效率

## 五、锁与并发

### 乐观锁 vs 悲观锁

| 策略 | 机制 | 适用场景 |
|------|------|---------|
| 乐观锁 | version 字段，更新时检查版本 | 高并发读多写少、冲突率低 |
| 悲观锁 | SELECT FOR UPDATE 行级锁 | 写冲突频繁、数据一致性要求高 |

### 死锁预防

- 固定加锁顺序（所有事务按相同顺序获取锁）
- 减小事务范围（最小化锁持有时间）
- 设获取超时（`LOCK_TIMEOUT`）
- 避免长事务持锁

### 分批处理

大批量操作拆小事务减少锁持有时间：
- 每批 500-1000 条，事务间释放锁
- 避免单事务锁定大量行导致其他查询阻塞

## 六、数据增长管理

| 策略 | 说明 |
|------|------|
| 分区 | 按时间/范围水平分区，减少单次扫描量 |
| 归档 | 历史数据定期迁移到归档表，保持主表精简 |
| TTL 清理 | 过期数据自动清除（日志/临时数据/过期会话） |
| 读写分离 | 主从复制分散读压力 |
| 索引维护 | 定期重建膨胀索引，更新统计信息 |

## 七、各引擎差异速查

| 特性 | SQLite | MySQL | PostgreSQL | MongoDB |
|------|--------|-------|-----------|---------|
| 并发模型 | 单写多读（WAL 模式） | 行锁（InnoDB） | MVCC 多版本并发 | 文档级锁 |
| 索引类型 | B-Tree | B+Tree / Hash | B-Tree / GIN / GiST | B-Tree / Text |
| 分页 | OFFSET 仅 | OFFSET / Keyset | OFFSET / Keyset / Cursor | skip / cursor |
| 连接池 | 单连接即可 | 池化必须 | 池化 + pgbouncer | 驱动内置池 |
| 适用规模 | 嵌入式/小并发 | 中大型 Web | 复杂查询/大数据 | 文档型/灵活模式 |
| 全文搜索 | FTS5 扩展 | FULLTEXT | GIN + tsvector | Atlas Search |
| JSON 支持 | json_extract | JSON 列类型 | JSONB（索引） | 原生文档 |
