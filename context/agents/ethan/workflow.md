# 系统设计工作流

## 1. 理解输入

读取已加载的需求、技术规范和项目上下文，提取功能点、验收标准、技术约束、影响范围和待确认项。

理解完成后，在回复中列出需要设计的所有模块和维度（含安全设计：认证授权、会话管理、输入边界等），再开始勘察和设计。

## 2. 项目勘察

用 `list_files`、`search_files`、`analysis_files` 和 `read_files` 找到相近模块或接口。记录项目在命名、分层、数据、接口、错误、权限、前端交互方面的实际模式。

## 3. 方案设计

设计以下内容：
- 文件结构：新增和修改文件及职责。
- 数据设计：模型、字段、状态、关联、迁移或兼容影响。
- 接口设计：方法、路径、参数、响应、错误、权限。
- 模块协作：调用关系、数据流、边界条件。
- 状态与生命周期：会话、缓存、锁等运行时状态的存储位置和方式、多进程部署与重启后的行为、并发访问的保护策略。
- 决策记录：关键选择、备选方案、取舍理由。

## 4. 一致性校验

检查设计是否符合项目事实、技术规范和需求验收标准。发现不一致时修正设计，不能用个人偏好覆盖项目约定。

## 5. 输出

按指令写入：
- `specs/design.md`：摘要，不放完整字段和接口详情。
- `tasks/design-{scope}.md`：模块详细设计。scope 粒度为独立功能模块（如用户管理、权限管理），不是应用或层级（如 admin、backend）。基础设施和公共代码可合为一个 scope。
- `tasks/api-contract-{scope}.md`：完整接口契约，scope 与 design 对齐。

scope 粒度判定：一个 scope 对应一个可独立开发、独立测试的功能模块。若一个 scope 内包含多个无直接依赖的功能（如用户管理和系统设置），应拆为多个 scope。

若未要求写入文档，则在回复中给出结构化设计。

## 完成检查

- 是否回溯指令要求，逐条确认每个要求的设计内容都已覆盖；若有遗漏则补充。
- 涉及认证、会话、权限的设计是否覆盖完整生命周期和安全边界。
- 是否读过至少一个相近实现或说明无先例。
- 是否列出新增和修改文件及职责。
- 是否覆盖数据、接口、权限、错误、边界条件。
- 是否记录关键设计决策及理由。
- 是否把摘要和详情分层，避免上下文膨胀。
- 是否没有把开发步骤、任务拆分或测试计划写成设计主体。
- 涉及运行时状态时，是否说明存储方式和多进程/重启下的行为。
- 设计是否符合需求文档（specs/requirement.md）中的关键约束：
  - 用户指定的架构模式和应用边界是否在设计中正确体现，未扩大或缩小范围。
  - 需求中的 Must 功能是否全部有对应设计模块。
- 设计是否符合技术规范（specs/tech-spec.md）中的命名、接口和数据格式约定。

## 6. 总结回复

回复中总结：设计了哪些模块、产出了什么文档、关键设计决策和待确认点。
