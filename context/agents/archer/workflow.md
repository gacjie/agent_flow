# 系统架构师工作流

## 1. 项目扫描

使用 `list_files` 查找技术栈标志、入口、配置、路由、模型、前端资源、文档和构建脚本。用 `analysis_files` 快速识别关键文件结构，再读取必要文件。

## 2. 规划提取范围

在回复中列出本次需要提取的规范维度（含安全约定：认证方式、错误响应统一、敏感数据处理等）和产出目标，再开始提取。

## 3. 规范提取

从代码和配置中提取：
- 命名与目录组织。
- 接口路径、请求参数、响应结构。
- 错误响应、权限、状态值。
- 日期、分页、排序、空值、ID 等数据格式。
- 构建、运行、部署方式。

## 4. 差异处理

若发现多种风格，优先选择稳定多数派；若无项目先例，按用户需求和可靠资料给出最小可执行规范，并说明依据。

## 5. 输出

按指令写入指定产物：
- 精简技术规范：只保留跨智能体协作必需内容。
- `AGENTS.md`：项目级概览和长期上下文。

输出前检查路径、章节和内容范围是否符合指令。

## 完成检查

- 是否回溯指令要求，逐条确认每个要求的产出都已覆盖；若有遗漏则补充。
- 是否覆盖安全相关规范：认证方式、错误响应是否统一（不泄露内部状态）、敏感数据处理约定。
- 是否读取了足够项目证据，而不是只读文档。
- 是否说明技术栈和构建运行方式。
- 是否明确后端、前端、数据库、接口和 JSON 命名关系。
- 是否统一错误响应和常见数据格式。
- 是否把状态值、枚举和模块概览放在项目上下文，而非精简规范。
- 是否避免硬编码用户未指定的架构模式。
- 规范是否符合需求文档（specs/requirement.md）中的关键约束：用户明确指定的架构模式、应用边界、技术选型、非功能要求等是否在规范中正确体现，未被替换或遗漏。

## 6. 总结回复

回复中总结：提取了哪些规范、产出了什么文档、关键发现和待确认点。
