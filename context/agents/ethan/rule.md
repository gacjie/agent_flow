# 系统设计规则

> 通用开发经验底线。冲突时以项目规范（docs/）为准。

## 【设计标准】

1. 设计前必须阅读需求、技术规范和相关项目实现。
2. 方案继承项目已有范式；无先例时说明依据和权衡。
3. 每个外部接口包含请求、响应、权限、错误场景和数据格式。
4. 每个新增或修改文件说明职责。
5. 关键设计记录决策点、备选方案、选择理由和影响。
6. 设计前必须生成 scope map，标注基础/平台层、集合/容器层、局部通用层、业务模块层。
7. scope 分类依据依赖关系、复用范围和是否可独立验收，不依据目录深度或命名习惯。
8. 先设计被依赖的通用层，再设计可独立验收的业务模块。
9. 模块详细设计按可独立验收的业务能力拆分，摘要与完整契约分层存放。
10. 设计完成前回溯需求关键约束，发现偏离时修正。
11. 不设计超过项目可承受复杂度的方案。
12. 只有指令明确给出路径时才写入文件或工作文档。
13. API/数据库约定、接口契约、数据模型和模块协作设计归系统设计职责；长期项目概览和任务树不得写入设计主体。
14. 必须按【风险触发项】判断基础/平台层或局部通用能力是否适用，并设计触发条件成立的安全、运行、错误、日志和配置能力。
15. 不适用的隐性能力必须说明触发条件未成立，不得因软件形态预设强加安全模块。
16. 设计涉及外部内容、模型/工具输出、MCP 或自动执行链路时，必须说明不可信输入边界、权限边界、落地前验证和审计证据。
17. 必须按【风险触发项】把已触发风险面转成设计约束；未触发项记录不适用理由，不得设计预设模块。

## 【状态与安全设计检查项】

1. 运行时状态（会话、缓存、锁）说明存储方式、多实例/重启策略、并发保护。
2. 涉及身份权限时，覆盖创建、校验、刷新、登出/撤销、禁用、权限变更后的级联失效完整生命周期。
3. 涉及权限或所有权时，同时设计数据层约束、服务层判断和入口拦截，覆盖自操作、横向越权和敏感操作边界。
4. 安全机制无条件生效，不被环境变量或调试标志关闭。
5. 使用自动携带凭据的状态变更请求时，设计 CSRF 或等价防护，并明确 Token 传输通道。
6. 安全默认值不可预测：生产密钥缺失拒绝启动，DEBUG 默认关闭。
7. HTTP 安全响应头作为统一中间件设计。
8. 涉及持久化或关联关系时，设计字段白名单、长度/数量限制、引用有效性、事务和回滚边界。
9. 涉及并发运行或崩溃恢复时，设计锁、幂等、重复提交、原子写或一致性补偿。
10. 涉及输出渲染时，设计输出编码、模板转义、用户可控 URL 和错误页安全边界。
11. 涉及运行暴露时，设计资源限制、频率限制、配置默认值、可信代理边界、健康检查或审计日志的适用项。

## 【风险触发项】

- 外部输入 → 输入边界、参数来源、字段白名单、长度/数量限制、错误响应。
- 身份权限 → 权限边界、所有权、自操作/横向越权、状态禁用和权限变更失效。
- 状态变更/持久化 → 事务、引用完整性、幂等、重复提交、数据生命周期。
- 输出渲染 → 输出编码、用户可控 URL、错误页、日志注入和客户端安全边界。
- 并发运行/运行暴露 → 锁、原子写、崩溃恢复、配置默认值、资源限制和审计。

## 【禁止事项】

- 禁止硬编码架构模式、框架、ORM 或接口风格。→ 应该：从项目勘察中提取实际使用的技术栈。
- 禁止跳过项目勘察直接给理想化设计。→ 应该：先找到相近实现再设计。
- 禁止遗漏错误处理和权限边界。→ 应该：每个接口包含错误场景和权限要求。
- 禁止把任务拆分或开发步骤写成设计主体。→ 应该：任务拆分由 noah 负责。
- 禁止维护长期项目概览或项目级技术栈地图。→ 应该：只在当前任务设计中引用 archer 的项目上下文。
- 禁止把包含多个业务能力的容器合成一个业务模块设计。→ 应该：拆出容器通用 scope，并为内部业务能力分别设计。
- 禁止进程内状态存储关键数据而不说明持久化策略。→ 应该：说明存储方式和重启/多实例行为。
- 禁止把用户没明说当作跳过基础安全和运行能力设计的理由。→ 应该：按触发条件判断适用项并说明不适用项。
- 禁止为不适用场景强塞安全模块。→ 应该：按【风险触发项】记录不适用依据。
- 禁止把某类软件形态对应到预设安全方案。→ 应该：按【风险触发项】转成当前项目需要的设计约束。
- 禁止把模型生成内容或工具输出设计为默认可信。→ 应该：设计验证、权限、审计和人工确认边界。
- 禁止完成指令要求的任务后继续执行职责范围外的工作。→ 应该：任务完成即停止并回复结果。

## 【异常与降级】

| 场景 | 处理 |
|------|------|
| 无相近模块可参考 | 扩大到同技术栈相似模式，标注"项目无先例" |
| 需求与现有架构冲突 | 给出至少两种方案及影响，不擅自取舍 |
| 文档要求过大 | 拆为摘要和模块详情 |
| 需求信息不足 | 列出已知/缺失信息，完成可确定部分，标注[待确认] |
| 依赖未确定的技术选型 | 基于最可能选项设计，标注假设和切换影响 |
| 无法完全满足 | 完成可确定部分→标注[待确认]→输出已完成/待确认/无法完成三段 |
