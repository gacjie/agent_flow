# 后端性能优化技能

> 后端性能风险识别和优化模式全面清单。设计师读取后按项目裁剪产出性能约束——过滤项目不涉及的性能面，将适用项转化为具体配置和方案。开发者按需读取识别性能陷阱。

## 一、性能风险触发项表

| 触发领域 | 具体触发项 |
|---------|-----------|
| 数据库查询 | 循环内查询(N+1)、无索引过滤/排序、SELECT *、WHERE函数导致索引失效、深页OFFSET |
| 连接管理 | 无连接池、池过大/过小、连接泄漏、无验证机制、混合负载竞争同池 |
| 缓存设计 | 无缓存热数据、无TTL上限、缓存穿透/雪崩/击穿、缓存与DB不一致 |
| 批量处理 | 逐条处理大数据集、无分批/游标、单事务锁大量行 |
| 并发控制 | 无限制并发、无背压/限流、无超时链路 |
| 资源生命周期 | 连接/句柄/goroutine未释放、无界增长的缓存/队列/日志 |
| API响应 | 无分页返回全量、响应体过大无压缩、无限流无限速 |

## 二、数据库性能

### N+1 查询问题

**识别模式**：ORM 惰性加载、循环内逐条查询（100 条记录 = 101 次 DB 往返）。

**解决方案**：
- 预加载/批量加载：`WHERE id IN (1,2,3...)` 将 N+1 降为 2 条查询
- JOIN FETCH：关联数据一次性加载（注意大数据集内存）
- DataLoader 模式：GraphQL 场景批量合并同类请求
- 框架方案：Django `select_related`/`prefetch_related`、GORM `Preload`/`Joins`、Hibernate `@BatchSize`

**检测**：APM 工具自动高亮、慢查询日志、关注占总 DB 时间 >5% 的查询。

### 查询优化核心

- EXPLAIN/EXPLAIN ANALYZE 分析执行计划，关注全表扫描(type=ALL)
- 只选需要的列，避免 SELECT *
- 避免 WHERE 函数：`WHERE YEAR(date)=2023` 改为 `WHERE date BETWEEN '2023-01-01' AND '2023-12-31'`
- 优化 JOIN：索引 JOIN 列、合适 JOIN 类型、JOIN 替代子查询
- 限制返回行数：WHERE 过滤 + LIMIT
- 分批处理大 INSERT/UPDATE 减少锁争用
- 更新统计信息帮助优化器决策

### 分页策略选择

| 特性 | Offset 分页 | Keyset/Cursor 分页 |
|------|-----------|-------------------|
| 性能 | O(n) 线性退化（深页慢） | O(1) 恒定性能 |
| 随机页访问 | 支持 | 不支持 |
| 数据一致性 | 可能重复/遗漏 | 稳定结果 |
| 实现复杂度 | 简单，ORM 原生支持 | 较复杂，需维护 cursor |
| 适用场景 | <10000条、管理后台 | 大数据集、API、信息流 |

复合 cursor `(updated_at, id)` 确保唯一排序。OFFSET > 10000 应警戒切换。

### 性能阈值

| 指标 | 目标 | 说明 |
|------|------|------|
| 单查询 | <100ms | 超过需优化 |
| API 响应 | <200ms | 用户可感知延迟阈值 |
| 慢查询 | >1s | 必须优化 |

## 三、缓存策略

### 五种缓存模式

| 模式 | 说明 | 适用场景 |
|------|------|---------|
| Cache-Aside | 应用自行管理缓存读写 | 最常用，灵活性高 |
| Read-Through | 缓存层透明代理读取 | 简化应用代码 |
| Write-Through | 写入同时更新缓存和 DB | 强一致性需求 |
| Write-Back | 先写缓存，异步写 DB | 高写入吞吐 |
| Write-Around | 写入跳过缓存直接写 DB | 写多读少场景 |

### 缓存层级

1. **HTTP 缓存头**（Cache-Control/ETag）— 浏览器和代理缓存
2. **应用级缓存**（Redis/Memcached）— 频繁访问的查询结果和计算值
3. **API 网关缓存** — 消除后端重复处理
4. **CDN 缓存** — 静态内容就近分发

### 三大故障模式

| 故障 | 触发条件 | 防护 |
|------|---------|------|
| 穿透 | 请求不存在的 key，每次穿透到 DB | 布隆过滤器/空值缓存（短 TTL） |
| 雪崩 | 大量缓存同时过期，DB 压力骤增 | 随机 TTL 抖动分散过期时间 |
| 击穿 | 热 key 过期瞬间大量请求穿透 | 互斥锁（singleflight）重建缓存 |

### 最佳实践

- 合理 TTL 平衡数据新鲜度和性能
- 事件驱动缓存失效（数据变更时主动清除）
- 监控缓存命中率（低于 90% 需排查）
- 故障降级：缓存可服务过期数据避免完全不可用

## 四、连接池与并发

### 连接池配置

- **池大小**：每节点 8-16 连接起点，压测确认最优值，预留 25% 容量应对突发
- **超时**：等待超时 3-5s、空闲超时回收不用连接、最大生命周期防连接老化
- **验证**：启用验证 SQL（`SELECT 1`）确保连接健康
- **隔离**：API 和后台任务独立连接池，读写分离
- **监控**：活跃/空闲连接数、等待时间、超时事件、池利用率 >80% 需扩容

### 限流设计

- **算法选择**：令牌桶（允许突发）/ 滑动窗口（平滑限流）
- **限流维度**：按用户/API Key 限制（非仅 IP），认证端点更严（5-10次/15分钟）
- **响应**：返回 429 + Retry-After 头，提供清晰错误信息

### 熔断器

三态自动故障检测，防级联故障：
- **关闭态**：正常请求通过
- **开启态**：连续失败后快速失败，不调用下游
- **半开态**：限制性重试，成功则恢复关闭态

### 三者协作

```
边缘限流(Rate Limit) → 内部节流(Throttle) → 依赖熔断(Circuit Breaker)
```

## 五、资源管理

### 泄漏防护

- defer/finally 确保资源释放（连接、句柄、锁）
- 设置请求超时，防止无限等待
- 健康检查端点监控服务状态
- APM 监控工具（New Relic/Datadog）识别泄漏

### 无界增长防护

- 缓存设容量上限 + LRU 淘汰
- 队列设深度限制 + 背压机制
- 日志设轮转策略（按天/大小轮转）

### 业务影响

- 100ms 延迟 = 1% 销售下降（Amazon 数据）
- 3s 加载 = 40% 用户离开
- 1s 延迟 = 7% 转化率下降

## 七、高风险反模式表

| 反模式 | 后果 | 正确做法 |
|--------|------|---------|
| 循环内逐条查询 | 100条=101次DB往返 | 批量 WHERE IN 或 JOIN 预加载 |
| OFFSET 分页深翻 | 第1000页需扫描100万行 | Keyset 分页 |
| 无限制并发请求 | 下游服务过载/级联故障 | 限流 + 熔断 |
| 全量返回无分页 | 内存溢出/响应超时 | 分页 + 字段过滤 |
| 缓存无过期时间 | 数据永不更新/内存无限增长 | 设 TTL + 主动失效 |
