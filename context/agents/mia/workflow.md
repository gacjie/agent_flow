# 技术文档工作流

## 1. 理解项目

先建立项目全貌理解：
- 读取项目 `AGENTS.md` 或已有文档，了解技术栈、目录结构、模块职责。
- 工作区 `specs/` 文档已自动注入系统提示词，从中获取需求和设计背景。
- 用 `list_work_docs(scope="tasks")` 查看任务文档，读取与本次变更相关的模块详情文档。

## 2. 阅读实现代码

用 `list_files`、`analysis_files`、`read_files`、`search_files` 读取本次变更涉及的实现、路由、模型、配置和测试。提取路径、字段、默认值、错误和权限。

## 3. 判断文档策略

根据项目状态选择策略：
- 新项目（无 `AGENTS.md` 或内容极少）：从零编写 `AGENTS.md` 全局概要 + `docs/` 详细文档。
- 已有项目（已有 `AGENTS.md` 和 `docs/`）：更新受影响的现有文档 + 为新功能补充文档。

## 4. 撰写文档

项目文档的目的是帮助后续 LLM 在新任务中快速理解项目（区别于工作区文档服务当前任务的多会话协作）。

**AGENTS.md**（全局概要，所有会话自动加载）：
- 技术栈、目录结构、模块职责、关键配置、部署方式、状态值等全局信息。
- 文档清单：每个 `docs/` 文件一行描述 + 文件名，供 LLM 按需读取。

**docs/ 目录**（详细内容，按需读取）：
- API 文档：端点、参数、响应、错误、示例。
- 模块说明：职责、入口、关键类型、注意事项。
- 使用指南：前置条件、步骤、结果验证。
- 变更说明：新增、修改、兼容性、迁移注意事项。

> 分层原则：读者只需 AGENTS.md 就能定位方向，需要细节时按文档清单读取 docs/ 对应文件。

## 5. 交叉验证

回读关键代码，核对路径、字段、类型、状态码、示例和错误说明。发现不一致时以代码为准。

## 6. 输出

写入项目文档路径，更新 `AGENTS.md` 文档清单。若指令指定工作区路径，再写入工作区文档。

## 完成检查

- 是否回溯指令要求，逐条确认每个要求文档化的内容都已覆盖；若有遗漏则补充。
- API 文档是否包含认证要求、权限说明和安全注意事项。
- 是否先读 AGENTS.md 和相关任务文档理解项目全貌。
- 是否先读实现代码再写文档。
- AGENTS.md 是否包含全局概要信息和文档清单。
- docs/ 文件是否包含足够详细的内容。
- 路径、字段、类型、状态码和默认值是否与代码一致。
- 示例是否完整且符合项目认证和请求格式。
- 是否标注代码与需求不一致的待确认点。
