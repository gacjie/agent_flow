# 任务规划速查

## 【工具选择】

| 目的 | 使用工具 | 使用时机 | 不要用于 |
|------|---------|---------|---------|
| 确认项目结构 | `list_files` | 填写或校验文件路径前 | 已知路径后重复列目录 |
| 判断文件职责 | `read_files` | 需要确认任务边界或模块归属时 | 无需源码细节时反复读取 |
| 建立文档映射 | `context_lists` / `analysis_contexts` | 识别 `tasks/` 下设计、接口、UI 文档 | 代替读取任务所需的具体文档 |
| 读取任务文档 | `read_contexts` | 需要确认某个 `task_doc` 内容时 | 首次粗略扫描全部文档 |
| 创建或更新任务 | `task_writers` | 写入阶段父任务、叶子任务或修正字段 | 只做口头规划 |
| 自检任务树 | `task_lists` | 创建后检查结构、状态、文档关联 | 代替创建任务 |
| 清理错误任务 | `task_deletes` | 发现重复、无效、错误任务且非进行中时 | 删除进行中任务 |

## 【任务字段决策】

| 字段 | 选择规则 |
|------|---------|
| 标签 | 后端用 `[Backend]` 或 `[Backend:Go/Python/PHP/Node]`（仅作为 mason 的语言线索）；展示层用 `[Frontend]`；不创建测试/审查标签 |
| 标题优先级 | `P0`=基础、公共、被依赖能力；`P1`=核心业务和主要页面；`P2`=增强、边界体验、非功能要求落地 |
| `priority` 字段 | P0 写 2，P1 写 1，P2 写 0 |
| `task_doc` | 模型/服务关联 `tasks/design-{module}.md`；接口实现关联 `tasks/api-contract-{module}.md`；页面优先关联 `tasks/ui-patterns-{module}.md` |
| `depends_on` | 只写同一技术栈、同一 phase 内真实前置任务 ID；跨前后端依赖用 phase 顺序和任务描述表达；无法确定依赖时在描述中标注“并行可执行” |

## 【层级识别】

| 层级类型 | 判定依据 | phase 排序 |
|---------|---------|-----------|
| 基础/平台层 | 启动、配置、注册、路由装配、基础类、公共异常、构建等底座能力 | 最先 |
| 集合/容器层 | 承载多个应用、插件、包、服务、页面域、租户或资源分组 | 基础之后 |
| 局部通用层 | 某容器内被多个业务模块复用的布局、权限壳、共享服务、公共组件 | 容器之后 |
| 业务模块层 | 可独立验收的用户能力，如登录、仪表盘、设置、权限、订单、报表 | 通用层之后 |

## 【常见判断】

| 遇到情况 | 正确做法 | 错误做法 |
|---------|---------|---------|
| 一个任务涉及多技术栈 | 拆为多个叶子任务，各自标签独立 | 混合标签 |
| 后端任务使用 Go/Python/PHP/Node | 保留具体 `[Backend:*]` 标签帮助 mason 读取技能 | 因语言不同拆给不同后端专家 |
| 一个功能同时涉及后端能力和展示层 | 拆为后端 phase 与前端 phase，并用 phase 顺序或任务描述表达依赖 | 合并到同一 phase |
| 同一业务模块包含 API 和页面 | 后端 API/数据 phase 先执行，前端页面/交互 phase 后执行 | 因模块相同就合并为一个 phase |
| scope 是应用/服务/插件/包/页面域 | 先按【层级识别】判断是否为容器或局部通用 | 直接当业务模块 |
| scope 内有多个可验收能力 | 拆成多个业务模块 phase，必要时先建局部通用 phase | 创建一个粗 phase |
| 通用能力被多个模块依赖 | 独立成通用层 phase，并排在业务模块之前 | 塞进第一个业务模块 |
| 无法确定依赖方向 | 标注"并行可执行"，不设 depends_on | 随意猜测依赖 |
| 模块过大（超 200k 上下文） | 按子功能再拆 | 创建超大 phase |
| 单任务涉及超 3 个文件 | 拆为按文件或子功能划分的任务 | 保留超大任务 |
| 页面任务存在 UI 规范文档 | 优先关联 `ui-patterns` | 只关联笼统设计 |
| 多个独立前端页面/路由 | 登录、仪表盘、用户管理、角色管理、系统设置等分别拆成多个 `[Frontend]` 业务 phase | 合并成一个“前端业务模块”phase |
| 单页面内含多个局部组件 | 表格、筛选、弹窗、详情卡片等可合并在该页面 phase | 为每个局部组件制造独立 phase |
| 多步向导或连续流程不可独立验收 | 可作为一个流程 phase，`phase_label` 明确“单一流程”边界 | 借流程名义合并多个独立页面 |
| 涉及性能、安全、兼容性等非功能需求 | 写入任务或验收条件 | 只规划功能路径 |
| 涉及外部内容/工具输出风险 | 写入信任边界、权限、验证和审计验收条件 | 只写功能任务 |
| 设计包含基础安全/运行能力 | 独立 P0 phase 或写入 P0 验收条件，并排在业务模块前 | 塞进业务模块顺手做 |
| 设计标注能力不适用 | 不创建任务，保留不适用说明 | 为了完整性编造任务 |
| 依赖链过深（A→B→C→D） | 重组 phase 减少串行瓶颈 | 保留过深链 |
| MVC 多应用示例 | 框架层→多应用层→admin 通用层→登录/仪表盘/设置等业务模块 | 把 admin 整体作为模块 |
| 前端页面域示例 | 全局前端底座→页面域/应用壳→域内通用组件→业务页面/交互模块 | 把整个前端或整个页面域作为模块 |
| 模板视图依赖后端数据 | 拆成后端数据准备 phase 和前端/模板展示 phase | 因数据依赖就交给后端专家做完整页面 |

## 输出结构参考（指令未指定时）

```text
标题：[P级][标签] 动词+对象 — 文件路径
描述：完成什么 + 涉及文件范围 + 验收条件 + 待确认点
detail：关键执行提示和边界
scope_type：基础/平台层、集合/容器层、局部通用层或业务模块层
task_doc：关联的详情文档路径
depends_on：同一技术栈、同一 phase 内依赖任务 ID，多个用逗号分隔
```
